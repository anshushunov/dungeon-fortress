# Разработка агентами

Статус: черновик процесса

## Принцип

Агенты выполняют реализацию, проверку и документирование, но репозиторий хранит
контекст независимо от конкретного агента и диалога. Каждая задача должна иметь
проверяемый результат и достаточно контекста для продолжения другим агентом.

## Роли

Роли назначаются на задачу, а не закрепляются навсегда:

- **Product / Game Design** — формулирует цель, игровой эффект, ограничения и
  критерии приёмки.
- **Simulation Design** — определяет модель данных, правила, формулы,
  детерминизм и крайние случаи.
- **Gameplay Engineering** — реализует вертикальный срез в движке.
- **Tools / MCP Engineering** — создаёт агентские интерфейсы к редактору,
  рантайму, логам и тестам.
- **QA / Simulation Testing** — строит воспроизводимые сценарии, инварианты,
  нагрузочные и регрессионные тесты.
- **Art Direction / Content** — ведёт стиль, промпты, происхождение и импорт
  сгенерированных материалов.
- **Review / Integration** — проверяет решение, тесты, документацию и
  совместимость с принятыми ADR.

Один агент может выполнять несколько ролей для маленькой задачи, но реализация и
критическая проверка по возможности разделяются.

## Поток изменения

1. Issue описывает проблему, игровой эффект и критерии готовности.
2. Существенный выбор сначала получает ADR со статусом `Proposed`.
3. Реализуется маленький сквозной срез.
4. Автоматические проверки подтверждают правила симуляции.
5. Агент проверяет игру через структурированный API и, если нужно, визуально.
6. Pull Request связывает код, тесты, документацию и решение.
7. После проверки документация отражает фактическое состояние системы.

## Целевой контур инструментов

После выбора движка агентский контур должен поэтапно получить:

1. запуск тестов, сборки и статического анализа одной командой;
2. запуск и остановку игры или отдельной сцены;
3. чтение структурированных логов и списка ошибок;
4. управление seed, временем и скоростью симуляции;
5. запрос состояния сущностей и систем;
6. выполнение игровых команд и воспроизводимых сценариев;
7. получение скриншотов и данных профилирования;
8. безопасный импорт созданных ассетов и проверку их параметров.

MCP будет удобным транспортом для этих возможностей, но доменные команды и
диагностические интерфейсы не должны зависеть от одного клиента MCP. Их следует
реализовать как тестируемый API/CLI, поверх которого можно сделать MCP-адаптер.

## Технологический радар

Раз в две недели и перед началом нового вертикального среза проверяются изменения
движка, .NET, MCP, тестовых и генеративных инструментов. Порядок проверки и
правила принятия обновлений определены в `TECH_RADAR.md`.
