# Правила входа агента

Этот блок prepended каждым запуском `take-task.ps1`. Агент обязан следовать ВСЕМ правилам ниже. Нарушение — блокирующий дефект.

## Обязательное чтение

Ровно два источника обязательны **всегда**, независимо от типа задачи:

1. `AGENTS.md` — общий контракт агента; подтягивается клиентом автоматически
   (Claude Code — через `CLAUDE.md`, который его импортирует; Codex читает
   `AGENTS.md` напрямую).
2. `docs/engineering/AGENT_ENTRY.md` — этот файл; печатается `take-task.ps1`
   целиком в начале каждого брифа.

**Решение координатора 2026-08-07 (Issue #282).** Раньше типовой бриф
требовал прочитать порядка десяти документов до первой строки работы:
`AGENTS.md`, `docs/README.md`, `VISION.md`, `PITCH.md`, разделы `ROADMAP.md`,
design-контракт прототипа, шесть ADR, `PROTOTYPE_HEADLESS.md` и
`PROTOTYPE_GRAYBOX.md`. Начиная с этого решения всё, кроме двух источников
выше, подтягивается **по признаку задачи**, а не читается по умолчанию — за
полноту пакета отвечает бриф координатора, а не память исполнителя. Основание
— уже действующее правило 13 `DEVELOPMENT_PACE.md`: «бриф самодостаточен,
несёт выдержки, а не ссылки; обязательное чтение содержит только то, что
бриф физически не может нести». Эта задача не вводит новое правило, а
приводит фактический пакет в соответствие с уже принятым.

**Цена решения названа прямо.** Ответственность за непрочитанное переносится
с исполнителя на координатора. Критерий готовности «ни одна задача не
проваливается из-за непрочитанного» остаётся в силе: если агент не знал
правила, которое обязан был знать, это дефект брифа координатора — повод
вернуть документ в обязательный список, а не упрёк исполнителю.

### Что подтягивается по признаку задачи

Признак — область, которую трогает задача (правило 19 `DEVELOPMENT_PACE.md`:
`симуляция + контракт`, `представление`, `tooling + docs`), и метка `tier:*`
(правило 34). `scripts/agent/take-task.ps1` печатает пакет по этой таблице
автоматически, определяя область по меткам Issue и по путям файлов,
названным в разделе «Партиция» его тела. Координатор может расширить пакет
вручную прямо в брифе, если задача сложнее, чем говорят метки и партиция, —
таблица задаёт минимум, а не потолок.

| Признак задачи | Что читать сверх двух обязательных источников |
|---|---|
| область `симуляция + контракт`: партиция называет `src/DungeonFortress.Simulation/**` или `docs/design/**`, либо метка `tier:deep`/`tier:critical` | раздел `docs/design/PROTOTYPE_01_PREPARE_FOR_RAID.md`, который описывает затронутую механику (якорь называет бриф); ADR из `docs/decisions/`, на которые этот раздел ссылается |
| область `представление`: партиция называет `src/DungeonFortress.Presentation/**` | `docs/engineering/PROTOTYPE_GRAYBOX.md` — запуск и воспроизводимый screenshot Phase A graybox; `docs/design/SIDE_INDICATOR.md`, если задача меняет индикацию стороны |
| headless-экономика: партиция или тело называют `PROTOTYPE_HEADLESS` или `tests/DungeonFortress.Scenarios` | `docs/engineering/PROTOTYPE_HEADLESS.md` |
| метка `tier:art` | `docs/art/ANIMATION_PIPELINE.md` |
| область `tooling + docs`: партиция называет только `docs/**`, `scripts/**`, `.claude/**` — без `src/**` | ничего сверх двух обязательных источников; код игры не читается |
| задача трогает продуктовое направление или продуктовое обещание | `docs/product/PITCH.md` и/или раздел `NOW` `docs/product/ROADMAP.md` — координатор несёт выдержку в бриф, а не общую ссылку на файл |

Если по меткам и партиции Issue область не определяется однозначно,
`take-task.ps1` печатает **полный** пакет (все строки таблицы выше) и прямо
говорит об этом в выводе секцией «Reading Package» — молчаливого урезанного
пакета не бывает: недостаток данных не повод угадывать.

## Изоляция

- **Корневая рабочая копия принадлежит координационной сессии.** НЕ ПЕРЕКЛЮЧАТЬ ветку и НЕ КОММИТИТЬ из неё.
- Ваша задача работает в своём worktree, созданном через `git worktree add`. Работать ТОЛЬКО внутри этого worktree.
- Если назначенная ветка или каталог уже существуют — НЕ затирайте. Сообщите и выйдите с ненулевым кодом.

## Партиция файлов

- Пишете только в те файлы, что перечислены в разделе «Партиция» брифа под пунктом «Своё».
- НЕ КАСАЕТЕСЬ ни одного файла из раздела «Чужое, не трогать».
- Если нужен файл вне вашей партиции — эскалируйте координатору; не модифицируйте самостоятельно.

## Никаких следов

- Не оставлять секреты, токены, локальные кэши и крупные производные файлы на машине хоста.
- Не изменять переменные среды, shell-профили и системную конфигурацию пользователя.
- Очистить временные артефакты перед завершением работы.

## Вложенные агенты запрещены

- По умолчанию вложенные сабагенты ЗАПРЕЩЕНЫ (правило 20). Каждая задача выполняется одним плоским вызовом агента.
- Если делегирование всё же необходимо — эскалируйте; не спавните молча.

## Рубежные коммиты

- Каждый коммит — проверяемый рубеж. Запускать `verify.ps1` (стадии, относящиеся к вашей области) на каждом коммите.
- Если полная проверка `verify.ps1` для вашей задачи не требуется — объяснить явно.

## Мутанты

- Если в задаче назначен мутант — условие мутанта ОБЯЗАТЕЛЬНО должно покраснеть при применении мутации; иначе покрытие тестов недостаточно.
- Отчёт о мутантах включить в итоговый handoff.

## Идентификатор модели

- Назвать точный идентификатор модели и версию сборки для любого сгенерированного контента.
- Формат: `model=<provider>/<name>:<version>` с хэшем коммита или тегом, если доступно.

## Числа с командой (правило 8)

- **Каждое число в отчёте идёт с командой, которой оно снято, либо со ссылкой на единственное место записи.** Без команды число — пересказ, и независимый review не может отличить измерение от приукрашивания, не перемерив всё сам.
- Пример: вместо «стадия scripts идёт 12,4 с» — «`Measure-Command { powershell -File scripts\verify.ps1 -Stage scripts }` → 12,4 с».

## Класс модели (правило 34)

- Класс модели задаётся меткой `tier:*` задачи, а не выбором исполнителя.

| Класс задачи | Класс модели |
|---|---|
| `tier:fast` | средняя (Sonnet 5) |
| `tier:standard` | средняя (Sonnet 5) |
| `tier:deep`, `tier:critical` | старшая (Opus 5) |
| независимый review | не ниже класса исполнителя |

- Младшая модель (Haiku) в проекте не используется.
- Эскалация — исполнитель поднимает класс сам, если задача оказалась сложнее назначенного, и называет признак в теле PR (не наоборот: понижать класс исполнитель не вправе).
- Источник правила и способ проверки исполнения — правило 34 [`DEVELOPMENT_PACE.md`](DEVELOPMENT_PACE.md).

## Потолок длины прогона (правило 35)

- Заканчивайте прогон коммитом и передаточным резюме ДО авто-компакции, а не после неё.
- Увидели авто-компакцию или предупреждение о заполнении контекста — немедленно доведите текущий рубеж до коммита и остановитесь. Не ждите следующего шага.
- Бриф называет плановый потолок вызовов (ориентир — 90) и `checkpoints`; приближение к потолку без завершённого рубежа — тоже повод остановиться и закоммититься.
- Передаточное резюме — сообщение коммита: что сделано, что осталось, какие файлы трогать дальше, какие проверки уже зелёные, коммит остановки.
- Источник правила, калибровка потолка и разбор наблюдаемости — правило 35 [`DEVELOPMENT_PACE.md`](DEVELOPMENT_PACE.md).

## Бриф

- В выдаче задачи обязательны: класс работы, оценка расхода токенов (диапазон с основанием), требуемый класс модели и бюджет рассуждений, условия эскалации, критерии готовности, мутант (если назначен).
- Если в брифе чего-то из этого нет — эскалируйте координатору, не начинайте работу молча.

## Формат отчёта

**Итог — это тело PR (правило 25).** Исполнитель сам создаёт PR в свою ветку, и тело PR И ЕСТЬ отчёт; отдельного handoff нет. Остановка и вопрос — комментарием в свою Issue. В теле PR обязательны:

1. Раздел **«До → Меняем → После»** (правило 16) — что было, что меняется, что получится.
2. Что изменено (файлы, коммиты).
3. Как проверено (команды + их результат, тесты, стадии verify, результаты мутантов) — каждое число с командой (правило 8).
4. Какие риски и ограничения остались.
5. Какие документы и решения обновлены.
6. Фактический расход токенов против оценки из брифа — с названием точного идентификатора модели.
7. **Для нового PR — строка «Независимый review ещё не проходил».** После каждого круга review тело обновляется так, чтобы review мог перепроверить правки.

## Язык артефактов

- Репозиторий русскоязычный. Тело PR, комментарии в Issues и отчёты пишутся **на русском**. Модель и команды — как есть.
