# Правила входа агента

Этот блок prepended каждым запуском `take-task.ps1`. Агент обязан следовать ВСЕМ правилам ниже. Нарушение — блокирующий дефект.

## Изоляция

- **Корневая рабочая копия принадлежит координационной сессии.** НЕ ПЕРЕКЛЮЧАТЬ ветку и НЕ КОММИТИТЬ из неё.
- Ваша задача работает в своём worktree, созданном через `git worktree add`. Работать ТОЛЬКО внутри этого worktree.
- Если назначенная ветка или каталог уже существуют — НЕ затирайте. Сообщите и выйдите с ненулевым кодом.

## Партиция файлов

- Пишете только в те файлы, что перечислены в разделе «Партиция» брифа под пунктом «Своё».
- НЕ КАСАЕТЕСЬ ни одного файла из раздела «Чужое, не трогать».
- Если нужен файл вне вашей партиции — эскалируйте координатору; не модифицируйте самостоятельно.

## Никаких следов

- Не оставлять секреты, токены, локальные кэши и крупные производные файлы на машине хоста.
- Не изменять переменные среды, shell-профили и системную конфигурацию пользователя.
- Очистить временные артефакты перед завершением работы.

## Вложенные агенты запрещены

- По умолчанию вложенные сабагенты ЗАПРЕЩЕНЫ (правило 20). Каждая задача выполняется одним плоским вызовом агента.
- Если делегирование всё же необходимо — эскалируйте; не спавните молча.

## Рубежные коммиты

- Каждый коммит — проверяемый рубеж. Запускать `verify.ps1` (стадии, относящиеся к вашей области) на каждом коммите.
- Если полная проверка `verify.ps1` для вашей задачи не требуется — объяснить явно.

## Мутанты

- Если в задаче назначен мутант — условие мутанта ОБЯЗАТЕЛЬНО должно покраснеть при применении мутации; иначе покрытие тестов недостаточно.
- Отчёт о мутантах включить в итоговый handoff.

## Идентификатор модели

- Назвать точный идентификатор модели и версию сборки для любого сгенерированного контента.
- Формат: `model=<provider>/<name>:<version>` с хэшем коммита или тегом, если доступно.

## Числа с командой (правило 8)

- **Каждое число в отчёте идёт с командой, которой оно снято, либо со ссылкой на единственное место записи.** Без команды число — пересказ, и независимый review не может отличить измерение от приукрашивания, не перемерив всё сам.
- Пример: вместо «стадия scripts идёт 12,4 с» — «`Measure-Command { powershell -File scripts\verify.ps1 -Stage scripts }` → 12,4 с».

## Бриф

- В выдаче задачи обязательны: класс работы, оценка расхода токенов (диапазон с основанием), требуемый класс модели и бюджет рассуждений, условия эскалации, критерии готовности, мутант (если назначен).
- Если в брифе чего-то из этого нет — эскалируйте координатору, не начинайте работу молча.

## Формат отчёта

**Итог — это тело PR (правило 25).** Исполнитель сам создаёт PR в свою ветку, и тело PR И ЕСТЬ отчёт; отдельного handoff нет. Остановка и вопрос — комментарием в свою Issue. В теле PR обязательны:

1. Раздел **«До → Меняем → После»** (правило 16) — что было, что меняется, что получится.
2. Что изменено (файлы, коммиты).
3. Как проверено (команды + их результат, тесты, стадии verify, результаты мутантов) — каждое число с командой (правило 8).
4. Какие риски и ограничения остались.
5. Какие документы и решения обновлены.
6. Фактический расход токенов против оценки из брифа — с названием точного идентификатора модели.
7. **Для нового PR — строка «Независимый review ещё не проходил».** После каждого круга review тело обновляется так, чтобы review мог перепроверить правки.

## Язык артефактов

- Репозиторий русскоязычный. Тело PR, комментарии в Issues и отчёты пишутся **на русском**. Модель и команды — как есть.
