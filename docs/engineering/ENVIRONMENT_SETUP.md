# Настройка окружения Godot/.NET spike

Статус: действует для bootstrap-spike из Issue #3

Дата проверки: 2026-07-29

## Закреплённые версии

- [.NET SDK 8.0.423](https://dotnet.microsoft.com/en-us/download/dotnet/8.0);
- [Godot 4.7.1 stable, .NET edition](https://godotengine.org/download/archive/4.7.1-stable/);
- PowerShell 5.1 или новее для локальных Windows-скриптов.

`global.json` закрепляет SDK 8.0.423 с переходом только на более свежий patch в
той же feature band. Godot-проект использует `Godot.NET.Sdk/4.7.1`; локальный
NuGet source берётся из `GodotSharp/Tools/nupkgs` выбранной .NET-сборки движка.

## Обязательные компоненты

1. Установить .NET SDK и проверить:

   ```powershell
   dotnet --version
   ```

   Ожидается `8.0.423` или совместимый patch, разрешённый `global.json`.

2. Скачать и распаковать Godot 4.7.1 .NET edition в пользовательский каталог вне
   репозитория. Установка export templates для этого spike не требуется.

3. Сделать console executable доступным одним из четырёх способов, в порядке
   приоритета:

   - передать `-GodotPath <path-to-godot-console>`;
   - установить `GODOT4_CONSOLE`;
   - добавить каталог в `PATH` под именем `godot4_console`, `godot4` или `godot`;
   - **(Issue #307) ничего не настраивать** — положить распакованный движок в
     каталог `Godot_v4.7.1-stable_mono_win64` рядом с корнем репозитория
     (`<родитель репозитория>\Godot_v4.7.1-stable_mono_win64\`, тот же уровень,
     на котором Issue #302 уже создаёт свой временный каталог и на котором
     `git worktree add` создаёт рабочие копии). Этот способ читает диск, а не
     переменные окружения, и поэтому не зависит от того, унаследовал ли
     процесс переменные, заданные в другом сеансе — см. следующий пункт.

   Первые три способа читают состояние текущего процесса (аргумент, переменная,
   `PATH`) и поэтому ненадёжны в сценарии, где процесс не наследует переменные,
   заданные после его запуска, — например, для агента в оболочке, поднятой до
   того, как `GODOT4_CONSOLE` был прописан в пользовательском окружении
   (`evidence/307-resolution.json`). Четвёртый способ читает диск напрямую и не
   зависит от этого; он рассматривается последним, чтобы явные способы
   по-прежнему могли его переопределить.

   Пример настройки только для текущего PowerShell-процесса:

   ```powershell
   $env:GODOT4_CONSOLE = "<path-to-godot-console>"
   ```

Скрипты проверяют строку версии `4.7.1` и наличие bundled NuGet packages. Путь
конкретной машины не записывается в проект. Каталог другой версии рядом с
корнем репозитория (например, оставленный от предыдущей проверки движка)
резолвится четвёртым способом так же, как и любой другой кандидат, — отвергает
его именно эта проверка версии, называя найденную версию, а не сам резолвер.

## Временный каталог

Проверке нужен временный каталог, в котором она может создавать, писать **и
удалять**. Там живут две вещи: короткий runtime profile Godot и изолированный
проект теста импорта спрайтов. Обе создаются во время прогона и убираются после.

Каталог выбирается в порядке:

1. `-TemporaryRoot <path>` — явный одноразовый override;
2. `$env:DUNGEON_FORTRESS_TEMP` — override для всей сессии;
3. **собственный каталог прогона** (Issue #302): без первых двух пунктов
   `verify.ps1` больше не читает системные `TMP`/`TEMP` вовсе. Он сам вычисляет
   короткое имя рядом с корнем репозитория — `<родитель репозитория>\df-verify-<8
   hex>`, например `C:\gamedev\df-verify-1a2b3c4d` для worktree
   `C:\gamedev\_wt-302` — создаёт его и удаляет после прогона.

**До Issue #302 третий пункт читал системные `TMP`/`TEMP`, и это было дефектом,
не удобством.** Оболочка агента разрешает `TMP`/`TEMP` в `C:\WINDOWS\TEMP`, где
этот аккаунт может создавать, но не может удалять: каждый прогон без override
отказывал в preflight — **независимо** от того, работал ли рядом другой агент.
За сессию 2026-08-07 это случилось минимум пять раз (PR #290 дважды, #291,
#297, #298, #299) и читалось как состязание нескольких агентов за общий
каталог. Измерение в `evidence/302-temp-contention.json` — два прогона `-Stage
scripts,build` одновременно из разных worktree, оба без `-TemporaryRoot` —
показало, что дело не в состязании: тот же отказ с той же причиной
воспроизводится и от **одного** прогона без каких-либо параллельных агентов,
потому что `C:\WINDOWS\TEMP` недоступен на удаление этому аккаунту вообще.
«Состязание» было интерпретацией агентов, которым каждый раз приходилось
вручную подбирать одноразовый `-TemporaryRoot`, а не свойством среды.
Умолчание больше не читает `TMP`/`TEMP` совсем, поэтому переменные ОС имеют
значение только если сам агент передаст `-TemporaryRoot`/`$env:DUNGEON_FORTRESS_TEMP`
на такой путь явно.

### Прогон не оставляет следов в среде машины

Временный каталог решает только половину задачи: он ограничивает, **где** прогон
пишет файлы, и ничего не говорит о том, что прогон может дописать в среду
пользователя. Одна такая утечка измерена и закрыта 2026-08-02.

**Что случилось.** Пользовательский `PATH` владельца вырос до **13 302 символов и
145 записей**, из которых **135** — хвосты вида
`…\dotnet-home\.dotnet\tools`, оставшиеся от worktree'ов и temp-прогонов, чьих
каталогов давно нет. `PATH` близок к пределу, после которого Windows перестаёт
его разрешать целиком, и ни один из этих путей ничего не даёт.

**Причина измерена двухармовым экспериментом, а не выведена из документации.**
Свежий `DOTNET_CLI_HOME` плюс любая команда, поднимающая first-run experience
(проверялось на `dotnet new console`), дописывает `<CLI_HOME>\.dotnet\tools` в
`HKCU\Environment\Path`:

| Арм | Переменные | Записей в `PATH` |
|---|---|---|
| A — как было в скриптах | `DOTNET_CLI_HOME` + `DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1` | **+1** |
| B — то же плюс guard | и `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0` | **+0** |

Каталог `<CLI_HOME>\.dotnet\tools` при этом не создаётся **ни в одном** из армов:
guard влияет только на запись в `PATH`, а запись появляется при отсутствующем
каталоге. Проверено обоими армами независимого review 2026-08-02.

То есть `DOTNET_SKIP_FIRST_TIME_EXPERIENCE` от этой записи **не защищает** —
распространённое заблуждение, и скрипты проекта задавали её в шести местах,
считая вопрос закрытым.

**Правило.** Каждое место, задающее изолированный `DOTNET_CLI_HOME`, задаёт рядом
`DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0`. Проверка — `rg -n "DOTNET_CLI_HOME"
scripts/` и `rg -n "DOTNET_ADD_GLOBAL_TOOLS_TO_PATH" scripts/` обязаны давать
одинаковое число попаданий.

**Сегодня они его не дают, и это известное нарушение, а не недосмотр.** Мест с
`DOTNET_CLI_HOME` шесть — `run-game.ps1`, `evaluate-prototype.ps1`,
`update-golden-ui.ps1`, два в `ivan-mcp.ps1` и `verify.ps1`, — а guard стоит в
**пяти**. Не хватает его в `scripts/verify.ps1`, самом часто запускаемом скрипте
проекта: файл держала параллельная задача подключения пака существ v2, и строка
уходит туда её коммитом. Дыра закрывается вместе с merge той пары; до тех пор
`rg` даёт 6 против 5, и это ожидаемо.

**Как убрать уже накопившееся.** Записи безопасно удаляются целиком — каталогов
нет. Настоящий каталог глобальных инструментов `%USERPROFILE%\.dotnet\tools`
признака `dotnet-home` не содержит и под фильтр не попадает:

```powershell
# DoNotExpandEnvironmentNames обязателен — см. ниже, почему Get-ItemProperty здесь непригоден
$raw = (Get-Item 'HKCU:\Environment').GetValue('Path', '', 'DoNotExpandEnvironmentNames')
$kept = $raw -split ';' | Where-Object { $_ -ne '' -and $_ -notmatch 'dotnet-home' }
Set-ItemProperty 'HKCU:\Environment' -Name Path -Value ($kept -join ';') -Type ExpandString
```

**Две ловушки, каждая уничтожает данные молча.**

*Тип.* `setx` пишет `REG_SZ` и режет значение на 1024 символах, поэтому он здесь
не годится вовсе; `-Type ExpandString` обязателен.

*Содержимое.* `Get-ItemProperty` возвращает **развёрнутое** значение. Обратная
запись с правильным типом сохранит тип и потеряет содержимое: `%USERPROFILE%\…`,
`%APPDATA%\npm`, `%JAVA_HOME%\bin` навсегда станут жёсткими путями, и заметить
это нельзя — на текущей машине они разрешаются в то же самое. Поэтому читать
**только** через `GetValue(..., 'DoNotExpandEnvironmentNames')`. Найдено
независимым review 2026-08-02 и доказано на отдельном временном ключе:
`Get-ItemProperty` вернул `C:\WINDOWS\system32;C:\literal` там, где сырое
значение — `%SystemRoot%\system32;C:\literal`.

Бэкап снимается **тем же** сырым вызовом. Бэкап, снятый через
`Get-ItemProperty`, не восстанавливает исходное состояние: он уже развёрнут, и
отличить по нему «ссылок не было» от «ссылки развернулись» невозможно. Ровно так
и вышло при первой уборке на машине владельца — исходная форма записей
пользовательского `PATH` там потеряна, хотя `HKCU` этой машины ссылками
пользуется (`TEMP`, `TMP`, `GOPATH`).

**Шире правила.** То же относится к любому следу в среде: реестр, глобальные
конфиги инструментов, домашний каталог. Прогон, который нельзя повторить тысячу
раз без накопления, считается дефектным, даже если каждый отдельный запуск
проходит зелёным.

Выбранный каталог печатается до первой стадии и попадает в итоговую строку:

```json
{"event":"verification_temporary_root","status":"ok","path":"C:\\gamedev\\df-verify-1a2b3c4d","source":"own run directory","owned":true}
```

`source` называет, откуда взят каталог: `-TemporaryRoot`, `$env:DUNGEON_FORTRESS_TEMP`
или `own run directory`. `owned` истинно только для третьего варианта — только
такой каталог `verify.ps1` удаляет сам после прогона; каталог, названный явно
через параметр или переменную, мог быть выбран для переиспользования между
прогонами и не трогается.

Пригодность проверяется **до** запуска стадий: скрипт создаёт пробный подкаталог
с файлом и удаляет его — тем же вызовом `Remove-Item -Recurse -Force`, которым
пользуется настоящая уборка. Непригодный каталог отвергается с указанием
каталога, причины и способа исправления, а `verification_result` получает
`"failedPhase":"preflight"` и пустой `stagesExecuted`.

Пример из сессии, в которой `TEMP` указывал в `C:\WINDOWS\TEMP` — до Issue #302
это был каталог по умолчанию, сегодня то же самое воспроизводится, только если
кто-то сам передаст `-TemporaryRoot C:\WINDOWS\TEMP` или укажет его через
`$env:DUNGEON_FORTRESS_TEMP`:

```text
The temporary directory this run would use is not usable.
  directory: C:\WINDOWS\TEMP
  chosen by: -TemporaryRoot
  failure:   'C:\WINDOWS\TEMP\verify-temp-probe-...' was created and then could
             not be deleted: Отказано в доступе.
Use one of:
  -TemporaryRoot <directory this account can create and delete in>
  $env:DUNGEON_FORTRESS_TEMP=<the same directory>
Without either, this run computes its own directory next to the repository
root and TMP/TEMP are not consulted (Issue #302) - pointing TMP/TEMP
elsewhere will not change what this run picked.
```

Так выглядит Issue #89. До проверки пригодности та же сессия доходила до стадии
`godot`, тест импорта печатал `status: ok`, и только его уборка падала на
`Remove-Item`. Прогон сообщал `{"failedStage":"godot","reason":"'powershell'
failed with exit code 1."}` — сообщение не называло ни каталог, ни право, и три
разные сессии искали дефект в проверяемом изменении.

Тонкость, из-за которой проверка делает удаление именно через `Remove-Item`: в
`C:\WINDOWS\TEMP` вызов `[IO.Directory]::Delete` на собственном подкаталоге
проходит, а `Remove-Item -Recurse -Force` на нём же падает с
`Access is denied`. Проба более дешёвым вызовом признала бы каталог пригодным, а
уборка всё равно упала бы.

Это правило держится не комментарием. `test-temporary-root.ps1` утверждает по
AST, что **первое** удаление и в пробе, и в настоящей уборке — это
`Remove-Item` с `-Recurse`, `-Force` и `-ErrorAction Stop`. Без утверждения
подмена прошла бы незамеченной: в тестах удаление блокируется открытым файлом, а
на открытом файле падают оба вызова, и разница между ними видна только на правах
`C:\WINDOWS\TEMP`.

Убирает за собой проба в два шага. Решение принимается по результату первого
вызова — того самого, что делает настоящая уборка. Если он отказал, каталог
пробы дополнительно удаляется через `[IO.Directory]::Delete`, который именно
там срабатывает. Иначе отвергнутый прогон оставлял бы каталог навсегда:
перечислить `C:\WINDOWS\TEMP` под этим аккаунтом нельзя вовсе, и найти мусор
можно было бы только по пути из сообщения об отказе. Сообщение говорит, чем
кончилась уборка, и не обещает мусора, которого нет.

**Без override каталог подбирается автоматически** (Issue #302) — но не
угадыванием, а вычислением по тому же правилу, каким сам был бы обязан
руководствоваться человек, выбирающий `-TemporaryRoot` вручную: коротко и вне
worktree. Каталог обязан быть коротким и вне worktree, потому что в нём
создаётся runtime profile Godot, а за 254 символами движок перестаёт входить в
собственный shader cache — см. [«Длина пути профиля Godot и shader
cache»](#длина-пути-профиля-godot-и-shader-cache). Подставить `.artifacts/`
внутри worktree вместо системного temp — ровно тот случай, на котором открылся
Issue #184: `DUNGEON_FORTRESS_TEMP=.artifacts/tmp` из worktree дал `APPDATA`
длиной 110 символов и 14 строк ошибки, и та же арифметика повторилась при
выборе умолчания для #302 — вложенный per-run каталог внутри `.artifacts`
worktree'а `_wt-302` (`C:\gamedev\_wt-302\.artifacts\verify-temp-<32 hex>`)
оставлял всего 17 символов запаса вместо измеренных для `.artifacts` без
вложенности 36; цифры и четыре промеренных варианта — в
`evidence/302-default-root-path-length.json`. Поэтому умолчание — короткое имя
рядом с корнем репозитория (`<родитель репозитория>\df-verify-<8 hex>`), а не
внутри `.artifacts` и не по пути системного `TMP`/`TEMP`. Прогон по-прежнему
отказывается угадывать непроверенный каталог: вычисленное умолчание проходит
ту же пробу пригодности, что и явный `-TemporaryRoot`, и слишком глубокий или
недоступный на запись/удаление отвергается по имени до запуска движка, а не
молча.

Неудача уборки — предупреждение, а не провал. Если каталог перестал удаляться
уже после проверки пригодности (антивирус, открытый файл, редактор), в выводе
появляется строка

```json
{"event":"temporary_cleanup","status":"warning","description":"...","path":"...","reason":"..."}
```

а прогон сохраняет тот статус, который заслужили сами проверки. Выполненная
проверка не становится красной из-за того, что каталог не удалось стереть.

Обе половины правила проверяются отдельным dependency-free тестом из стадии
`scripts`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-temporary-root.ps1
```

Он подтверждает порядок выбора каталога, отвергает файл вместо каталога и
каталог, из которого не удаляется содержимое, требует, чтобы пригодный каталог
принимался и не оставлял мусора, и запускает настоящий `verify.ps1` с заведомо
непригодным `-TemporaryRoot`, ожидая отказ с пустым `stagesExecuted`. Удаление
блокируется настоящим открытым файлом, а не заглушкой. Плюс описанное выше
AST-утверждение о способе удаления — с **пятью** мутациями копии
`TemporaryRoot.ps1`, на которых оно обязано сработать, и контрольным прогоном на
неизменённой копии. Утверждение закрепляет не наличие `-ErrorAction`, а его
**значение** `Stop`: измерено, что на файле, удерживаемом открытым, более слабое
значение заставляет пробу вернуть «каталог пригоден» сразу после того, как она
не смогла его удалить.

Issue #302 добавил три проверки поверх этого: без override источник — не
`TMP/TEMP`, а `own run directory`, и не внутри каталога-приманки, подставленного
вместо системного temp; вычисленное умолчание по-прежнему проходит пробу
пригодности — файл, заранее положенный по предсказанному пути (тот же
`-Suffix`, что и в реальном прогоне, только фиксированный), отклоняется с той
же диагностикой «это файл, не каталог»; и `Complete-VerificationTemporaryRoot`
— функция, которую вызывает `finally`-блок `verify.ps1` — реально удаляет
каталог, помеченный `Owned=$true`, и никогда не трогает каталог с
`Owned=$false` (явный `-TemporaryRoot`/`$env:DUNGEON_FORTRESS_TEMP`). Третья
проверка — **не** сквозной прогон настоящего `verify.ps1`: первая версия
запускала `verify.ps1 -Stage scripts` без `-TemporaryRoot` и проверяла итог,
но эта стадия сама включает `test-temporary-root.ps1`, поэтому такой прогон
рекурсивно запускал сам себя и раздул один `-Stage scripts` до 240 секунд
вместо обычных десятков. Проверка вызывает `Complete-VerificationTemporaryRoot`
напрямую, в процессе — то же поведение, без дочернего дерева процессов; сквозная
демонстрация со настоящим `verify.ps1 -Stage scripts` без параметров всё равно
существует, но как разовая команда для evidence (`evidence/302-temp-contention.json`),
а не как часть каждого прогона `test-temporary-root.ps1`.

## Единая проверка

### Требование к запуску проверок агентом

Читать **до** первого прогона, а не после третьего неудачного.

Оболочка агента — не оболочка владельца, и расходилась она в двух местах, оба
из которых больше не обязательны:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

**Движок — больше не требует `-GodotPath` (Issue #307).** `GODOT4_CONSOLE`
задан в пользовательском окружении владельца, но оболочкой агента **не
наследуется** — она форкается до того, как переменная была прописана, и
дочерние процессы Windows не перечитывают окружение родительского аккаунта
после старта. То же самое, тем же самым способом, не наследует и `PATH`.
Раньше это делало `-GodotPath` обязательным для агента: первые три способа
разрешения движка (явный параметр, `GODOT4_CONSOLE`, `PATH`) все читают
состояние процесса, а не диск, и все три поэтому пусты в такой оболочке даже
на полностью настроенной машине — измерено в `evidence/307-resolution.json`.
Четвёртый способ, добавленный Issue #307 и описанный в «Обязательных
компонентах», читает диск напрямую: каталог `Godot_v4.7.1-stable_mono_win64`
рядом с корнем репозитория. На машине, где движок распакован по этой
конвенции, `verify.ps1` резолвит его без параметров и без переменных из любой
оболочки, включая ту, что не унаследовала окружение владельца. `-GodotPath`
по-прежнему работает и по-прежнему в приоритете — он нужен только когда эта
конвенция расположения не выполняется (движок лежит не рядом с репозиторием,
или на машине несколько версий и требуется другая, а не самая новая).

**Временный каталог — больше не обязателен (Issue #302).** До этого Issue
оболочка агента разрешала `TMP`/`TEMP` в `C:\WINDOWS\TEMP`, куда этот аккаунт
может писать, но не может удалять, и `verify.ps1` отказывал в preflight на
каждом прогоне без явного `-TemporaryRoot` — независимо от того, работал ли
рядом другой агент; подробности и измерение — раздел [«Временный
каталог»](#временный-каталог) и `evidence/302-temp-contention.json`.
`verify.ps1` больше не читает `TMP`/`TEMP` по умолчанию: без параметра он
вычисляет собственный короткий каталог рядом с корнем репозитория и удаляет
его сам после прогона. `-TemporaryRoot <путь>` или `$env:DUNGEON_FORTRESS_TEMP`
по-прежнему работают и переопределяют умолчание — например, чтобы переиспользовать
каталог между несколькими прогонами подряд, что умолчание сознательно не
делает (оно каждый раз создаёт и полностью убирает новый).

Оба пункта стоили нескольким агентам по нескольку неудачных прогонов, прежде
чем факт и его причина попали в этот документ, — Issue #302 для временного
каталога, Issue #307 для движка, — поэтому оба записаны здесь как объяснённое
поведение, а не как обязательный параметр, который нужно помнить.

**Исключение: `-Stage scripts` и `-Stage token-budget`.** Две стадии, чьи тела
не вызывают ни `dotnet`, ни движок: `scripts` (Issue #285; измерение —
`evidence/285-stage-engine-need.json` в PR, закрывшем issue) и `token-budget`
(Issue #310, вынесена из `scripts` тем же основанием — её тело тоже чистый
PowerShell). Preflight резолвит движок, только если среди выбранных стадий
есть хотя бы одна, кроме этих двух, поэтому `.\scripts\verify.ps1 -Stage
scripts` и `.\scripts\verify.ps1 -Stage token-budget` проходят без
`-GodotPath`, без `GODOT4_CONSOLE` и без `-TemporaryRoot` — умолчание Issue
#302 покрывает и этот случай. Любая другая стадия — в том числе в сочетании со
`scripts`/`token-budget` — снова требует движок: `build`, `tests` и `mcp`
собирают решение целиком, `sim` и `load` восстанавливают его через
`Initialize-ScenarioAssembly`, а `godot`, `ui` и `screenshots` запускают сам
исполняемый файл. Отказ по-прежнему называет стадию, которая потребовала
движок, например `Stage(s) godot require the Godot engine...`.

### Обычный запуск

Из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

Для явного одноразового override:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -GodotPath "<path-to-godot-console>"
```

введением стадий не изменился.

порядке таблицы; `-Stage` оставляет подмножество, `-Skip` исключает названные.

Маркеры вокруг неё не декоративные: без них сверка не знает, какую таблицу читать,
и падает.

от их числа. На машине агента `.\scripts\verify.ps1 -Stage token-budget`

без изменений в самом тесте, только тёплый кэш после повторных сканирований
одной и той же директории. Ровно поэтому тест не годится ни одной другой
стадии, кроме собственной: цена определяется состоянием диска, а не тем, что
проверяет код.

Что покрывает каждая стадия, печатает сам скрипт:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -ListStages
```

Примеры частичного прогона:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -Stage ui
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -Stage tests,sim
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -Skip load,screenshots
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 -Stage all
```

`-Stage all` — явный псевдоним полного прогона: он раскрывается в весь список
стадий и даёт `scope: full`, то есть равен запуску без `-Stage`. Пригоден, когда
имя стадии подставляется скриптом или переменной и «все» нужно выразить
значением, а не отсутствием параметра. Имя `all` занято псевдонимом и не может
быть именем стадии.

Любая стадия, включая `scripts`, требует установленного Godot. Движок
разрешается один раз до цикла стадий, потому что NuGet-профиль для .NET-сборок
пишется из bundled packages выбранной сборки движка. Обход сделал бы частичный
прогон проверкой не того же, что проверяет полный: сборка пошла бы с
machine-wide NuGet state. Поэтому «dependency-free» в описании стадии `scripts`
означает «без сборки решения и без запуска движка», а не «без установленного
движка».

### Какую стадию выбирать

| Что изменено | Минимальный набор |
|---|---|
| `scripts/**`, evidence/auth tooling, конфигурация MCP-клиентов | `scripts`; плюс `mcp` при правке launcher или `verify-domain-mcp.ps1` |
| `src/DungeonFortress.Simulation/**` | `tests,sim`; плюс `load` при изменении стоимости тика или структур данных; плюс `mcp` при изменении ответа `prototype_run` |
| `src/DungeonFortress.Presentation/**` | `tests,ui` |
| `src/DungeonFortress.Game/**`, сцены, ввод | `godot,ui`; плюс `screenshots` при изменении кадра или визуального слоя |
| спрайты и другие ассеты | `godot,screenshots` |
| `.csproj`, `global.json`, версии зависимостей | полный прогон |
| только документация | ничего |

Стадия сама доводит рабочую копию до нужного состояния: `-Stage ui` выполнит
restore, `Debug` build Godot-host и импорт ассетов, `-Stage sim` соберёт scenario
runner. Поэтому частичный прогон не проверяет вчерашний бинарник, а выполненные
подготовительные шаги перечислены в поле `prerequisites`.

Сам механизм стадий тоже проверяется, и без сборки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-verify-stages.ps1
```

Тест разбирает как AST **четыре файла** — `verify.ps1` и все скрипты, которые он
дот-сорсит: `GodotTools.ps1`, `HudVerification.ps1` и `TemporaryRoot.ps1`, — и
держит три инварианта, ни один из которых не виден в зелёном прогоне. Разбирать
только `verify.ps1` было дырой: PR #97 добавил в `$allowedOutsideStages` два
имени, указывающих в файл, который guard никогда не открывал. Цель дот-сорса
берётся из двух литеральных написаний, а всё остальное отвергается: файл,
который guard не может назвать, — это файл, который он не может проверить.

**Ни одна проверка не живёт вне стадии.** Правило задано списком **мест**, а не
списком известных имён проверок. Тело стадии и тело любой функции, достижимой из
стадии, могут содержать что угодно — для этого стадия и нужна. Верхний уровень и
тело функции, до которой не дотягивается ни одна стадия, могут вызывать только
имена из `$allowedOutsideStages`. Подготовка прогона живёт в дот-сорсенных
функциях, их тела разбираются тоже и могут вызывать `$allowedOutsideStages` плюс
плумбинг из `$allowedInsideRunSetup`. Добавление имени в любой из списков —
отдельная строка в diff с обоснованием рядом.

Проверка под именем, которого guard никогда не видел, падает по умолчанию **на
верхнем уровне `verify.ps1` и в любой функции, недостижимой из стадий**. Внутри
подготовки прогона — **нет**, и это стоит знать точно, а не считать правило
одинаковым везде. Там имя допускается **по достижимости, а не по разрешению**:
функция, определённая в дот-сорсенном файле и вызванная из подготовки, входит в
её замыкание под любым именем, после чего guard разбирает уже её тело. Проверка,
собранная из разрешённого плумбинга, так проходит. Это не отдельная дыра, а
отложенный пункт 2 из решений Issue #102 под видом имени функции; точная
формулировка живёт в шапке `test-verify-stages.ps1`, и она первична по отношению
к этому абзацу. Негативный случай `check-inside-dot-sourced-run-setup`
доказывает ту часть, которая держится, — имя, которое вызвано, но нигде не
определено, — и большего из него выводить не следует.

Прежняя версия перечисляла известные имена проверок, и review PR #70 прошёл
сквозь неё: `Assert-SomeNewInvariant` внутри `try` перед циклом стадий возвращал
`status: ok`.

**Всё, что вызывает `dotnet`, идёт до переключения `APPDATA`.**
`Initialize-GodotRuntimeEnvironment` переписывает `APPDATA` на короткий runtime
profile Godot, в котором нет NuGet-конфигурации. Guard моделирует порядок
выполнения по AST с учётом мемоизации подготовительных шагов и проверяет каждую
одиночную стадию и каждую упорядоченную пару стадий — то есть любой выбор,
который можно попросить через `-Stage`. Раньше инвариант держался комментарием.
Заодно фиксируется порядок подготовки до цикла стадий: временный каталог,
разрешение движка, версия, NuGet source, NuGet-профиль.

Имя `dotnet` сравнивается по написанию, а не по буквам: регистр, суффикс `.exe`
и каталог в пути отбрасываются, поэтому `dotnet`, `DotNet.exe` и полный путь до
`dotnet.exe` — одно и то же. Значение переменной по-прежнему **не** разрешается,
но нераспознанным `-FilePath $переменная` больше не остаётся: с Issue #102 это
**находка** guard'а, а не молчание. Разница принципиальная — модель порядка
читает значение как текст, поэтому программа, названная не строковым литералом,
была для неё невидима, и отсутствие выглядело точно так же, как соблюдение
правила. Осознанно открытыми оставлены два случая, и они названы прямо в тесте:
вызов вида `& $tool` и всё, что запускает дочерний скрипт.

**Таблица стадий совпадает со скриптом.** Сверка читает таблицу между маркерами
`<!-- stage-table:begin -->` и `<!-- stage-table:end -->`, а не «первую ячейку в
обратных кавычках» — иначе будущая посторонняя таблица со строкой вида
``| `assets` | … |`` дала бы ложное «documented but absent».

Кроме того, тест требует, чтобы неизвестное имя стадии и пустой выбор
отвергались, и проверяет сам себя: **одиннадцать** мутаций во временной копии
всего набора скриптов (проверка вне стадии под новым именем и через переменную,
проверка внутри дот-сорсенной подготовки прогона, проверка на верхнем уровне
модуля, цель дот-сорса через переменную, имя программы через переменную,
`dotnet` после переключения профиля и он же в написании `DotNet.exe` полным
путём, переставленные подготовительные шаги, недостижимый prerequisite,
удалённый preflight временного каталога), две мутации документа
(посторонняя таблица игнорируется, удалённая строка ловится) и контрольный
прогон на неизменённой копии, без которого негативные случаи не доказывали бы
ничего. Копируется весь набор, а не один файл, поэтому контроль заодно
доказывает, что строки дот-сорса разрешаются и когда дерево лежит не в
`scripts\`. Тест входит в стадию `scripts`.

### Когда полный прогон обязателен

Частичный прогон — инструмент итерации, а не замена проверки. Полный прогон
обязателен:

- перед handoff, PR и merge: `green-auto-merge` из
  [ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) требует зелёный
  `scripts/verify.ps1` целиком;
- после изменения зависимостей, версии SDK или движка;
- когда изменение затрагивает больше одной области из партиции ADR 0014;
- когда неясно, что именно затронуто.

Отличать прогоны нужно по выводу, а не по памяти. Итоговая строка
`verification_result` содержит `scope` (`full` или `partial`), `stagesExecuted` и
`stagesNotRun`:

```json
{"event":"verification_result","status":"ok","scope":"partial","stagesExecuted":["ui"],"stagesNotRun":["scripts","build","tests","mcp","sim","load","godot","screenshots"]}
```

Прогон, упавший на середине, печатает ту же строку со `"status":"error"`, именем
упавшей стадии и списком всего, что не выполнялось. Молча усечённой проверки не
бывает: частичный прогон всегда называет то, что он не проверял.

### Полный вывод стадий — в файле, не в stdout

Issue #284. Каждый прогон Godot внутри стадии печатал в stdout не только свой
результат, но и весь собственный вывод процесса — до нескольких десятков
килобайт JSON на один вызов (подписи HUD с пиксельными размерами, все
проверенные разрешения, тултипы, состав ростера). Замер зелёного полного
прогона до правки — `evidence/284-stdout-volume.json`: 352330 байт, 96 % из
которых — именно эти построчные дампы, ни разу не прочитанные, потому что
ничего не упало.

Полный вывод по-прежнему собирается, стадия за стадией, но пишется в файл
каталога прогона. Путь печатается один раз, одной строкой, до первой стадии:

```json
{"event":"verification_stage_output","status":"ok","path":"C:\\gamedev\\_wt-284\\.artifacts\\verify-<guid>\\stage-output.log"}
```

В stdout на зелёном прогоне остаются только: эта строка, `verification_temporary_root`,
по одной строке `verification_stage` на стадию (статус и время) и итоговый
`verification_result` — **со всеми** контрольными суммами. Файл живёт там же,
где остальное содержимое каталога `.artifacts/verify-*`, и подчиняется тому же
best-effort правилу уборки (см. «Временный каталог» выше): на зелёном прогоне
он, как правило, удаляется вместе с каталогом, и это не проблема — открывать
его на зелёном прогоне незачем.

Провал стадии остаётся диагностируемым **из stdout**, без открытия файла.
Вызов, который действительно упал (ненулевой exit code, строка `ERROR:`,
отсутствие ожидаемого success-события), печатает свой дамп и структурный
отчёт как раньше — обычным `Write-Host`, безусловно. Дополнительно, если
стадия упала уже после того, как несколько её собственных проверок прошли
успешно и увели свой вывод в файл (например снятие контрольной суммы,
провалившееся после трёх удачных запусков сценария), итоговый блок ошибки
восстанавливает из файла последние строки именно этой стадии — реальный
пример на `evidence/284-real-stage-failure.json`.

Проверку можно запускать с подключённым domain MCP: клиентская сессия исполняет
собственную копию сервера и не держит открытым build output. Останавливать
сессию перед `verify.ps1` не нужно — см. «Project-owned domain MCP».

Временные NuGet-настройки, пакеты и результаты создаются под `.artifacts/`,
который игнорируется Git. При первом запуске нужен доступ к NuGet.org для
тестовых пакетов; Godot packages берутся из выбранного движка. Runtime Godot
получает отдельный короткий профиль под системным temporary directory, чтобы
NuGet tool-profile из длинного worktree path не становился его `APPDATA`.

### Проверка вывода Godot

`run-game.ps1` и `verify.ps1` не считают exit code 0 достаточным условием успеха.
Общий guard завершает команду с code 1 при любой строке `ERROR:`, при ненулевом
exit code или при отсутствии ожидаемого structured success event. Широкого
whitelist нет.

Guard имеет отдельный dependency-free тест:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-godot-output-guard.ps1
```

### Корневая рабочая копия: гард правила 17 (Issue #253)

Правило 17 (`AGENTS.md`, «Работа нескольких агентов») отдаёт корневую рабочую
копию координационной сессии: записывающий агент не переключает в ней ветку и
не коммитит из неё. За четыре дня правило нарушено трижды тремя разными
способами, при том что оно уже было записано текстом:

| Дата | Что произошло | Наблюдаемый след |
|---|---|---|
| 2026-08-01 | art-задача дважды переключила `HEAD` корневой копии на свою ветку во время идущей координации | `HEAD` корня не на `main` |
| 2026-08-03 | [#202](https://github.com/anshushunov/dungeon-fortress/issues/202) велась и коммитилась в корневой копии на ветке `agent/202-worktree-command` (`git reflog` корня; запись в `DEBT_LEDGER.md`, добавленная review PR #213/#214) | `HEAD` корня не на `main` |
| 2026-08-04 | art-дорожка [#243](https://github.com/anshushunov/dungeon-fortress/issues/243) создала свой worktree **внутри** корневой копии (`w243`) | worktree, зарегистрированный по пути внутри корня |

Первые два случая — один и тот же наблюдаемый след с разных причин: корень
переключён на чужую ветку. Третий — другой след: `git worktree list`
регистрирует путь внутри корня, а `HEAD` самого корня при этом может
оставаться на `main`. Механизм состоит из двух узкоспециализированных
гвардов, по одному на след, а не одного с двумя обязанностями:

- **`scripts/check-root-on-main.ps1`** (новый, Issue #253) — ловит первый
  след. Определяет, что переданный `-RepoRoot` — это **главная** рабочая
  копия, а не связанный worktree, сравнивая `git rev-parse --path-format=absolute
  --git-dir --git-common-dir`: у главной копии оба пути совпадают, у
  связанного worktree `--git-dir` указывает под `.git/worktrees/<имя>` и не
  совпадает с `--git-common-dir`. Если это главная копия и её `HEAD` не на
  `main` — гард падает и называет найденную ветку. Если это не главная копия
  (то есть любой worktree любой задачи, включая тот, из которого сам агент
  сейчас запускает `verify.ps1`) — гард молча проходит: инвариант не
  относится к рабочим копиям задач, у которых ветка отличная от `main` — это
  нормальное, ожидаемое состояние.
- **`scripts/check-no-worktrees-in-root.ps1`** (существовал с Issue #287, PR
  #297; этой задачей впервые подключён и впервые получил тест) — ловит
  второй след. Читает `git worktree list --porcelain` и падает, если путь
  какого-либо зарегистрированного worktree (кроме самого корня) лежит внутри
  `-RepoRoot`.

Оба вызываются в `scripts/verify.ps1` реально — против того `-RepoRoot`, из
которого выполняется сам прогон, — первыми двумя действиями стадии `scripts`,
то есть до стадии `build` и до любой длинной стадии. Это тот же принцип, что
и у пробы временного каталога выше: дешёвый и фундаментальный гард идёт
первым.

**Почему `verify.ps1`-гард, а не гард в `take-task.ps1`, а не `.gitignore`.**
Ни один из трёх исторических случаев не был бы предотвращён гардом внутри
`scripts/agent/take-task.ps1`: `take-task.ps1` и так всегда вычисляет путь
worktree как `<родитель корня>\_wt-<номер>` — сиблинг, никогда не внутри
корня, — и ни один из трёх случаев не создавался этим скриптом. Случай
2026-08-01 и случай `#202` — это переключение ветки **в уже существующей**
корневой копии, `take-task.ps1` создаёт новый worktree и к этому моменту не
имеет отношения; случай `#243` — worktree, созданный вручную командой
`git worktree add`, в обход `take-task.ps1` вовсе. Гард в `take-task.ps1`
проверял бы дисциплину инструмента, который и так уже делал всё правильно, и
не видел бы ни одного из трёх настоящих нарушений. `.gitignore`-строка,
названная в Issue #253 как самый слабый вариант, была отвергнута по той же
причине, по которой она названа слабой в самой постановке: она прячет
`w243`/подобный каталог из `git status`, но не мешает ни коммиту из корня, ни
регистрации worktree внутри него — снимает видимость, а не причину.

**Известный предел механизма.** Оба гарда реагируют только на **выполненный**
прогон `scripts/verify.ps1` (стадия `scripts` или полный прогон) — они не
подписаны ни на какое событие git и не запускаются сами. Это прямо признанное
ограничение, а не недосмотр: правка `#202` была markdown-only и по
собственному телу PR #213 полный `verify.ps1` на ней не гонялся вовсе
(«ни одна из девяти стадий этот файл не читает»), а `#243` мог провести
сколько угодно времени незамеченным, если прогон в это время не выполнялся в
корне. Правило 17 остаётся защищено настолько, насколько агенты запускают
`verify.ps1` в корневой копии, — то есть механизм делает нарушение видимым
**в момент прогона**, а не гарантирует прогон.

Оба гарда — dependency-free и покрыты фикстурным тестом, использующим
одноразовый git-репозиторий под `.artifacts/`, а не настоящую корневую
копию:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-check-root-on-main.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-check-no-worktrees-in-root.ps1
```

Мутантные проверки (подстановка реального нарушения на фикстуре, а не на
корне) — `evidence/253-mutant-head-not-main.json` и
`evidence/253-mutant-worktree-in-root.json`; проверка, что механизм не
краснеет на законном состоянии (сиблинг-worktree рядом с репозиторием, корень
на `main`) — та же пара файлов и `evidence/253-legitimate-state.json`.

### Длина пути профиля Godot и shader cache

Во время review PR #5 исходный `run-game.ps1` воспроизводимо давал:

```text
ERROR: Condition "err != OK" is true.
   at: initialize (drivers/gles3/shader_gles3.cpp:802)
```

Та же строка вернулась в Issue #184 четырнадцатью экземплярами подряд и стала
поводом разобрать причину до числа. **Прежнее объяснение этого раздела — предел
`CreateDirectory` в 248 символов — на Godot 4.7.1 неверно и заменено.** Оно
проверено и отвергнуто: девять прогонов с холодным кэшем и путями shader cache
от 246 до 312 символов не дали ни одной строки. Godot вызывает
`CreateDirectoryW` с префиксом `\\?\`, для которого `MAX_PATH` не действует, а
`LongPathsEnabled` в `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem` на этой
машине равен `0` — то есть дело в префиксе движка, а не в настройке Windows.

**Что происходит на самом деле.** Каталог кэша Godot создаёт через
`CreateDirectoryW` с префиксом, а **входит** в него через `SetCurrentDirectoryW`
— без префикса, и вот на него `MAX_PATH` действует. Начиная с некоторой длины
каталог можно создать один раз и больше никогда в него не войти, поэтому

```cpp
if (d->change_dir(base_sha256) != OK) {
    Error err = d->make_dir(base_sha256);
    ERR_FAIL_COND(err != OK);
}
```

в `ShaderGLES3::initialize` уходит в ветку `make_dir` на уже существующем
каталоге, получает `ERR_ALREADY_EXISTS` и печатает строку — по одной на класс
шейдера.

Отсюда два следствия, на разбор которых Issue #184 потратил три прогона:

- **первый процесс всегда молчит.** Он и создаёт каталоги; шумит второй и каждый
  следующий. В стадии `screenshots` три захвата подряд, поэтому на холодном кэше
  шум приходится на второй процесс, а на тёплом — на первый. Ничего не
  «плавает»;
- **число строк — это число классов шейдеров, чей путь перешёл предел.** У этого
  проекта их четырнадцать (`CanvasOcclusionShaderGLES3`, `CanvasSdfShaderGLES3`,
  `CanvasShaderGLES3`, `CopyShaderGLES3`, `CubemapFilterShaderGLES3`,
  `FeedShaderGLES3`, `GlowShaderGLES3`, `ParticlesCopyShaderGLES3`,
  `ParticlesShaderGLES3`, `PostShaderGLES3`, `SceneShaderGLES3`,
  `SkeletonShaderGLES3`, `SkyShaderGLES3`, `TexBlitShaderGLES3`), и «14 строк»
  означает «перешли все».

**Предел измерен, а не процитирован: 254 символа.** Шесть арм по одному захвату,
профили от 90 до 110 символов `APPDATA`, каждая с очищенного кэша; число строк
совпало с числом каталогов длиной 255 и больше во всех шести — 0, 1, 3, 6, 14,
14. Армы, команды и вывод — `evidence/184-cause.json`.

**Между 254 и пределом самого API — четыре символа, и они не объяснены. Не
«исправляйте» константу на 258.** Прямые зонды к Win32 через P/Invoke (сделаны
независимым review PR #199) дают у `SetCurrentDirectoryW` без префикса границу
**258**: `len=258` входит, `len=259` отказывает с
`err=206 ERROR_FILENAME_EXCED_RANGE`; на пути формы Godot граница та же,
`LongPathsEnabled` равен `0`. То есть цепочка «вход без префикса → на него
действует `MAX_PATH`» объясняет направление, но не последние четыре символа:
движок перестаёт работать уже на 255, а голый API — только на 259. Откуда
берётся остаток, **не установлено**: между `ShaderGLES3::initialize` и
`SetCurrentDirectoryW` лежит `DirAccessWindows` со своим текущим каталогом и
своими переходами, и разбирать это дальше задаче не требовалось.

Поэтому **254 — калибровка по поведению движка, а не следствие предела API**.
Она предсказала все шесть арм, включая промежуточные 3 и 6. Сдвиг на 258 «по
документации Windows» вернёт Issue #184 целиком: в полосе 255–258 API работает,
а движок — нет. Основанием ослабить константу может быть только новая лестница
прогонов движка, а не зонд к API.

**Правило.** Каталог профиля Godot обязан оставаться коротким, и это больше не
просьба к читателю. `Initialize-GodotRuntimeEnvironment` измеряет самый длинный
путь shader cache, который движку понадобится, **до** запуска движка и
отказывается запускать его сообщением, называющим каталог, длину, число классов
за пределом и способ исправления. Зелёный прогон печатает тот же замер:

```json
{"event":"godot_runtime_profile","status":"ok","path":"C:\\Users\\User\\AppData\\Local\\Temp\\df-godot-978c4ffb\\Roaming","userDirectory":"Dungeon Fortress — deterministic spike","longestShaderCachePathLength":221,"maximumEnterablePathLength":254,"headroom":33}
```

Если движок всё-таки напечатает эти строки — например, в будущей версии с более
длинным именем класса, — guard по-прежнему уронит прогон, но теперь приложит к
`godot_process_guard` поле `engineErrorClass: "gles3_shader_cache_path"` и
объяснение, по которому строку не придётся искать в исходниках Godot.

**Оба способа поднять движок выбирают временный каталог одинаково.** Именно это
и было различием Issue #184: `verify.ps1` уважал `-TemporaryRoot` и
`$env:DUNGEON_FORTRESS_TEMP`, а `run-game.ps1` — нет, поэтому один и тот же кадр
снимался в двух разных профилях, и предел переходил только один из них. Теперь
`-TemporaryRoot` есть и у `run-game.ps1`, `update-golden-ui.ps1` и
`test-goblin-sprite-import.ps1`, а `test-godot-output-guard.ps1` перечисляет
скрипты сам и роняет прогон, если какой-нибудь из них снова начнёт поднимать
движок, не выбрав каталог общим способом.

`run-game.ps1` при этом делает только **выбор** каталога, без пробы на удаление:
право удалять нужно проверке, а не одиночному видимому запуску, и требовать его
здесь значило бы отказывать контрольному эксперименту ровно в той оболочке, где
он чаще всего и нужен.

Исправление PR #5 — разделить длинный NuGet tool-profile и короткий Godot
runtime profile — этим не отменяется: оно и сейчас единственная причина, по
которой обычный прогон укладывается в предел с запасом (`headroom` выше — 33
символа в этом worktree). Неверным было объяснение, а не действие.

**Побочный факт, который стоит знать.** Такой профиль потом нельзя удалить
`Remove-Item`: PowerShell 5.1 ходит через API .NET Framework, а они
останавливаются на `MAX_PATH`. Прогон, оставивший слишком глубокий профиль,
оставляет его навсегда, пока его не уберёт что-нибудь long-path aware
(`robocopy /MIR` из пустого каталога). Это ещё одна причина отказывать до
запуска движка, а не после.

## Производные файлы Godot и Git

Godot создаёт рядом с исходниками файлы, которых нет в коммитах: каталог кэша
`**/.godot/`, `*.import` рядом с каждым ассетом и `*.uid` рядом с каждым
скриптом. Все три восстанавливает тот же incremental-импорт, который
`verify.ps1` и `run-game.ps1` выполняют перед запуском движка, поэтому чистый
`git clone` полноценен без них.

### `*.uid` не отслеживаются — правило без исключений

Ни один `*.uid` не коммитится. Правило закреплено строкой `*.uid` в
`.gitignore` рядом с `*.import` и действует на весь Godot-проект.

До Issue #64 правила не было ни одного: `Main.cs.uid` отслеживался, а
`HudButton.cs.uid` из PR #57 — нет. Каждый агент в свежем worktree получал после
первого импорта грязное дерево и тратил внимание на вопрос «моё ли это
изменение». Это независимо произошло у исполнителей #58 и #38.

**Почему игнорируем.** Ни один отслеживаемый файл проекта не ссылается на
`uid://`. `Main.tscn` подключает скрипт по пути —
`[ext_resource type="Script" path="res://Main.cs"]`, — спрайты и иконки
загружаются `GD.Load<Texture2D>("res://assets/…")` тоже по пути, а
`project.godot` называет главную сцену как `res://Main.tscn`. Проверка ищет
только по содержимому Git и должна ничего не находить:

```powershell
git grep -n 'uid://' -- src/DungeonFortress.Game
```

Идентификаторы в проекте есть, но живут они ровно в производных файлах:
`uid="uid://…"` внутри каждого `*.png.import` и строка в каждом `*.uid`. Оба
класса игнорируются и восстанавливаются одним и тем же импортом, так что
одинаковое обращение с ними — не новая политика, а распространение уже
действующей.

Что идентификатор ни на что не влияет, проверено экспериментом, а не выведено из
этого поиска. После удаления `Main.cs.uid` вместе с локальным кэшем `.godot/`
импорт выдал скрипту **другой** случайный идентификатор
(`uid://du80nvw2ghu16` → `uid://cw3gvuoooy3xo`), `Main.tscn` при этом не
изменился, а полный `verify.ps1` остался зелёным — включая headless smoke,
`--smoke-controls`, camera/input smoke с независимой проверкой live Camera2D,
отрицательные startup/HUD/camera проверки, четыре camera/frame/UI варианта, три
golden UI frame, сравнение checksum на 20 и 60 fps и три screenshot-прогона,
которые загружают сцену и все PNG.

**Почему не коммитим.** Вариант «коммитить все `*.uid`» проверен тем же
способом и технически работает: уже закоммиченный `.uid` импорт сохраняет и не
переписывает даже при удалённом кэше `.godot/`. Отвергнут он не за это. Он
требует, чтобы автор каждого нового `.cs` вручную добавил в коммит второй файл,
который ничего не значит для читателя diff. Ровно этот шаг пропущен в PR #57 и
породил Issue #64, и ни одна проверка его не ловит. Игнорирование не требует
дисциплины вообще и одинаково ведёт себя при любом числе новых скриптов.

### При добавлении нового `.cs` или ресурса

Ничего делать не нужно. Новый `*.uid` появится после первого импорта, будет
проигнорирован и в `git status` не попадёт. Добавлять его через `git add -f` не
следует: отслеживаемый `.uid` вернёт ровно то расхождение, которое закрыл
Issue #64.

### Когда решение придётся пересмотреть

Триггер один: в `.tscn`, `.tres` или `project.godot` появилась ссылка `uid://`.
Признак виден прямо в diff — у `[ext_resource]` или у заголовка `[gd_scene]`
возникает атрибут `uid=`.

Механизм, которым это происходит, ровно один: **сцену сохранил редактор Godot.**
Пока сцены правятся текстом, как просит комментарий в первых строках
`project.godot`, атрибут `uid=` не появляется — импорт его не дописывает, что
подтверждает неизменённый `Main.tscn` в эксперименте выше. Но редактор в этом
репозитории не экзотика: `project.godot` держит включённым плагин
`res://addons/godot_mcp/plugin.cfg`, а `scripts/ivan-mcp.ps1 -Action Open`
открывает настоящий редактор по [ADR 0004](../decisions/0004-dev-only-ivan-mcp.md).
Поэтому связь стоит помнить целиком: **редактор сохранил сцену → в сцене
появился `uid=` → правило игнорирования пересматривается отдельным Issue.**

Важно знать заранее, **как именно** такая ссылка ломается, потому что тихо.
Проверено на отдельном одноразовом проекте под `.artifacts/`: сцена с
`uid="uid://ck7jxbdtppw5b"` рядом с `path="res://Probe.gd"`, а локально
сгенерированный `.uid` содержит другой идентификатор. Godot 4.7.1 в этом случае:

```text
WARNING: res://Probe.tscn:3 - ext_resource, invalid UID: uid://ck7jxbdtppw5b
 - using text path instead: res://Probe.gd
```

Дальше сцена грузится по пути, скрипт подключается, процесс выходит с кодом 0, и
сам файл сцены Godot не переписывает. Это `WARNING`, а не `ERROR:`, поэтому
guard из `run-game.ps1` и `verify.ps1` его не поймает — он падает только на
`ERROR:` и на ненулевом exit code. Пока ссылок `uid://` нет, ловить нечего; как
только они появятся, расхождение придётся ловить не проверкой вывода, а этим
правилом.

### Стартовый кадр и масштаб интерфейса

У `run-game.ps1` больше **нет** умолчаний `-FrameSize` и `-UiScale`. Прежние
`1280x720` и `1.0` — это прямоугольник, под который свёрстан HUD, а не описание
чьего-либо монитора: на экране владельца они открывали маленькое окно с текстом
в 8–15 физических пикселей. Дважды, Issues
[#86](https://github.com/anshushunov/dungeon-fortress/issues/86) и
[#100](https://github.com/anshushunov/dungeon-fortress/issues/100).

Запуск без параметров теперь спрашивает экран:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-game.ps1
```

Правило целиком, из двух действий:

1. окно занимает **90 % рабочей области** того экрана, на котором оно открылось,
   и центрируется в ней. Не всю область: окно остаётся обычным, его можно двигать
   и тянуть, а оставшаяся десятая часть оставляет место заголовку;
2. масштаб интерфейса — **наибольший шаг из `1`, `1.25`, `1.5`, `1.75`, `2`, при
   котором в кадр ещё помещается прямоугольник вёрстки 1280×720**. Верхняя
   граница совпадает с `CameraView.MaximumUiScale`, то есть с максимумом, который
   разрешён явному `--ui-scale`.

Отдельного запроса DPI в правиле нет намеренно. Окно Godot на Windows
per-monitor DPI aware, поэтому экран с системным увеличением 200 % уже отдаёт
вдвое больше физических пикселей, и отношение из пункта 2 забирает это
увеличение само. Отдельный множитель по DPI посчитал бы его второй раз.

Измерено на машине агента: рабочая область `3072x1824` → кадр `2764x1641` при
масштабе `2` (логические 1382×820). На ноутбучном `1366x768` то же правило даёт
кадр `1280x720` при масштабе `1`, то есть ровно прежнее поведение.

**Изменение размера окна пересчитывает масштаб.** Это и есть Issue #86:
максимизация раньше отдавала все новые пиксели миру и оставляла HUD на
launch-time масштабе. Проверено на живом окне: старт `2764x1641` @ 2 →
максимизация `3072x1779` @ 2 → уменьшение до `1394x759` @ 1, HUD каждый раз
перерисовывается в новом масштабе.

#### Что при этом не изменилось

Воспроизводимая съёмка кадра **не может** попасть на это правило, и не потому,
что так задумано в скрипте, а потому что `ViewLaunchOptions.Parse` отказывается
создавать capture без всех пяти явных параметров `--tile-size`, `--camera-zoom`,
`--camera-position`, `--ui-scale` и `--frame-size`. `verify.ps1` и
`capture-evidence.ps1` передают их всегда, поэтому кадр, позиция и зум остаются
явными по [ADR 0008](../decisions/0008-three-quarter-projection.md).

Структурированный вывод называет, какой половиной правила воспользовался прогон:

```json
{"frameMode":"explicit","uiScaleMode":"explicit","autoFrameSize":null,"screenUsableRect":null}
```

Так выглядит любая съёмка. Машинно-зависимый `screenUsableRect` печатает только
тот прогон, который действительно спрашивал экран, поэтому в evidence-манифест
он попасть не может.

Без экрана — headless или монитор меньше 1280×720 — правило не применяется
вовсе: остаётся окно `1280x720` из `project.godot` при масштабе `1`, как было до
его появления.

Явные параметры продолжают работать и задаются независимо друг от друга:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-game.ps1 -FrameSize 1920x1080 -UiScale 1.5
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-game.ps1 -FrameSize 1920x1080
```

Второй кадр объявлен, а масштаб выведен из него по тому же правилу и даёт `1.5`.
Пара, оставляющая меньше 1024×720 логических пикселей, отвергается до запуска
движка, если кадр объявлен, и движком в остальных случаях.

#### Где живёт правило

Арифметика — `CameraView.AutomaticFrameSize`, `AutomaticUiScale`,
`FitsLogicalFrame` и `AssertStartupFramePolicy` в
`src\DungeonFortress.Presentation` — не зависит от движка. Это требование
[ADR 0011](../decisions/0011-presentation-layer-without-engine.md): правило
представления живёт в Presentation, а не в адаптере, иначе его проверяет только
глаз. В Godot-адаптере остаётся ровно то, для чего действительно нужен движок:
спросить display server про экран, подвинуть окно и пересчитать масштаб, когда
игрок изменил его размер.

#### Проверка правила

Арифметика правила проверяется на **каждом** старте — во всех smoke, во всех
golden UI capture и во всех screenshot из `verify.ps1`.

Прогон печатал ещё и число выполненных утверждений, `startupFramePolicyChecks`.
Оно удалено в #86. На него не опирались ни `verify.ps1`, ни тесты, ни эталоны:
review PR #107 отключил одно негативное утверждение, прогон остался зелёным, и
число осталось прежним. Guard — это throw; доказательство того, что throw живой,
теперь даёт `CameraViewTests`, роняя его с двух сторон — недостижимым минимумом
логического кадра и минимумом, который перестал что-либо отвергать.

Одиннадцать реальных размеров экранов от `1280x720` до `3840x2160` проверяются на
то, что выбранный шаг существует и лежит в разрешённом диапазоне, что окно
помещается в экран и не мельче прямоугольника вёрстки, что логический кадр не
опускается под минимум HUD и что следующий шаг вверх этот прямоугольник уже не
удержал бы. Пять размеров отдельной возрастающей лестницей проверяются на
монотонность; отдельный экран для неё нужен потому, что матрица монотонной не
является — ультраширокий `3440x1440` шире и ниже, чем `3044x1722`. Последнее
утверждение — негативное: guard минимального логического кадра обязан
отвергнуть пару `1280x720` при масштабе `2`.

Проверка сама проверена мутациями `CameraView.cs`: доля экрана `1.2` вместо
`0.9`, выбор всегда максимального шага, выбор всегда минимального шага и
обезвреженный guard минимума — каждая падает кодом 1 со своим сообщением,
немутированная копия остаётся зелёной.

Пятая мутация — прямоугольник вёрстки `1024x720` вместо `1280x720` — проверку
**не** роняет, и это правильно: она меняет выбор политики, а не нарушает её
инварианты. Утверждение доказывает согласованность правила, а не то, что
выбранный прямоугольник единственно возможный.

Поскольку утверждение engine-free, его вызывает и обычный юнит-тест без движка —
`CameraView.AssertStartupFramePolicy(ViewLaunchOptions.MinimumLogicalFrameSize)`.
Godot-адаптер вызывает его на каждом входе.

#### Уменьшение окна ниже минимального логического кадра

Автоматический масштаб — функция **только** от кадра. Раньше решение было
разделено пополам: адаптер спрашивал масштаб, спрашивал, помещается ли пара в
минимальный логический кадр, и при отрицательном ответе **не делал ничего** —
то есть окно, стартовавшее на масштабе 2 и сжатое ниже `1024x720` логических
пикселей, сохраняло масштаб 2 и второй раз уменьшало логическую площадь HUD.

Решение целиком переехало в `CameraView.AutomaticUiScale(frame, minimumLogical)`,
который отвечает и для кадров под минимумом, а адаптер присваивает результат
безусловно. Прежнего значения, которое можно было бы сохранить, не осталось.
Последовательность из живого окна проверена юнит-тестом:
`2764x1641 → 2`, `3072x1779 → 2`, `1774x1229 → 1.25`, `1000x700 → 1`.

#### Стартовый зум камеры

У `run-game.ps1` больше нет и умолчания `-CameraZoom`. Прежние `0.75` выбраны под
кадр 1280×720; на развёрнутом окне они оставляли карту 1120×640 нарисованной 1:1
посреди вдвое большего viewport — вторая половина Issue #86.

Правило: наибольший из объявленных уровней `0.5`, `0.75`, `1`, `1.5`, `2`, при
котором карта целиком помещается в тот прямоугольник, который HUD отвёл миру.
В авторском кадре это `0.75`, в развёрнутом окне владельца — `1.5`. Изменение
размера окна пересчитывает зум, **пока игрок не покрутил колесо**: после этого
зум принадлежит игроку, и за окном продолжает следовать только масштаб HUD.
Арифметика — `CameraView.AutomaticZoom`, там же и по той же причине, что и
остальное правило старта.

#### Читаемость HUD

Отдельное правило и отдельный guard: `DungeonFortress.Presentation.HudReadability`
задаёт минимальный **физический** размер текста и потолок логической плотности,
адаптер измеряет `GetThemeFontSize` у живых `Label` и передаёт замер. Подсказка
кнопки (Issue #127) измеряется тем же способом через постоянный невидимый
образец в дереве `_hudRoot`, а не через сам попап Godot, который туда не
входит. Подробности, таблица измерений по матрице кадров и негативные прогоны
`--smoke-hud-readability-regression` / `--smoke-hud-tooltip-readability-regression`
— в [`PROTOTYPE_GRAYBOX.md`](PROTOTYPE_GRAYBOX.md#hud-readability-guard).

## Project-owned domain MCP

Issue #4 добавляет engine-independent stdio adapter над тем же
`DungeonFortress.Simulation` и command document contract, что использует
scenario CLI. Перед первой client-сессией:

```powershell
dotnet restore .\tests\DungeonFortress.DomainMcp.Tests\DungeonFortress.DomainMcp.Tests.csproj --locked-mode
dotnet build .\DungeonFortress.sln -c Release --no-restore
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-domain-mcp.ps1 -NoBuild
```

После Release build trusted Codex project читает `.codex/config.toml`, а Claude
Code предлагает одноразово подтвердить project-scoped `.mcp.json`. Эти файлы не
содержат секретов и абсолютных путей. Server публикует только
`bridge_status`, legacy `simulation_run` и gameplay-v2 `prototype_run`; запуск
fixtures Prototype 1 описан в `PROTOTYPE_HEADLESS.md`, а подробный контракт,
pins, hashes и security
guards и rollback находятся в `MCP_EVALUATION.md`.

Для `prototype_run` fixture является единственным источником seed, состава
существ и command document: флаги legacy CLI `--seed` и `--agents` с prototype
fixture отвергаются, а не переопределяют сценарий. Command document проходит
полную preflight-валидацию до создания мира, поэтому ошибка в будущей команде не
может оставить частично выполненный прогон. Ответ инструмента содержит canonical
snapshot и явные секции `economy`, `labor`, `stations`, пригодные для проверки
агентом без анализа изображения.

### Запуск сессии отделён от цели сборки

Оба клиента поднимают сервер одной командой
`cmd /c scripts\domain-mcp-server.cmd`. Launcher копирует
`tools\DungeonFortress.DomainMcp\bin\Release\net8.0` в собственный каталог
сессии `.artifacts\domain-mcp-sessions\<id>` и запускает копию. Отдельного шага
подготовки нет, а при завершении сессии каталог копии удаляется.

Так сделано потому, что раньше сессия исполняла сам build output. Файл
`bin\Release\net8.0\DungeonFortress.DomainMcp.exe` оставался открытым на всё
время сессии, и шаг `dotnet build DungeonFortress.sln -c Release` в
`verify.ps1` падал с `MSB3027`, не дойдя ни до одного теста (Issue #38). Теперь
цель сборки и исполняемая копия — разные файлы, поэтому проверка проходит при
любом числе подключённых клиентов и не требует ручной остановки сессии.

Что важно знать про копию:

- копия снимается один раз, в момент старта сессии. Живая сессия продолжает
  исполнять её и после пересборки решения — новую сборку подхватит только
  следующая сессия. Раньше действовало то же правило (`--no-build` исполнял
  последний build output), но теперь у копии есть собственный момент фиксации,
  и его стоит помнить при проверке свежих правок домена через MCP;
- каталог копии создаётся рядом под именем `<id>.partial` и переименовывается
  целиком, поэтому исполняемый каталог никогда не бывает наполовину скопирован.
  На всё время сессии launcher держит открытым `<id>.lock`, и уборка чужих
  копий пропускает такую сессию, даже если копирование ещё идёт;
- копии, оставшиеся после аварийно снятых сессий, удаляются при следующем
  старте: их lock свободен и исполняемый файл никем не открыт;
- старт сессии одновременно со сборкой теоретически может скопировать смесь
  файлов: robocopy читает каталог, который в этот момент переписывает MSBuild.
  Окно — доли секунды, MSBuild повторяет копирование до десяти раз, поэтому на
  практике такого не наблюдалось. Если сессия ведёт себя странно после старта
  во время сборки, перезапустите её.

Launcher написан на `.cmd`, а не на PowerShell: `cmd` запускает сервер ровно с
теми дескрипторами stdin/stdout, которые клиент дал launcher, без промежуточного
слоя. Прямой запуск из PowerShell (`&`, `Start-Process`) так не работает — его
native command processor превращает вывод дочернего процесса в объекты конвейера
и переписывает его через host, поэтому JSON-RPC пришлось бы перекладывать между
процессами вручную. Это лишняя копия, лишняя буферизация и риск перекодировки на
пути протокола без выигрыша. `scripts\verify-domain-mcp.ps1` поднимает тот же
сервер из PowerShell с явным перенаправлением, но там PowerShell сам является
клиентом, а не прозрачным передатчиком.

`cmd` и `robocopy` делают запуск domain MCP Windows-only. Раньше `dotnet run`
был формально кроссплатформенным, но контур проверки репозитория и так
Windows/PowerShell (ADR 0003, ADR 0004), а CI на Ubuntu MCP не поднимает.

Обе стороны проверяются автоматически:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-domain-mcp-config.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-domain-mcp-launcher.ps1
```

Первый тест читает конфигурацию и текст launcher: оба project config должны
поднимать сервер через launcher, не содержать машинных абсолютных путей и не
возвращаться к исполнению build output; первая строка launcher обязана быть
`@echo off`, а каждая его диагностика и вывод `robocopy` — уходить не в stdout.
Второй запускает launcher по-настоящему после сборки: проверяет ответ на
`initialize`, что сервер исполняет свою копию, что build output в это время
остаётся доступен на запись и что после закрытия stdin launcher вышел с кодом 0
и убрал за собой. Оба входят в `verify.ps1`; текстовый тест не заменяет запуск,
потому что опечатка в batch не видна в тексте.

Чтобы отключить domain MCP без удаления user-scope данных:

- Codex: установить `mcp_servers.dungeon_fortress_domain.enabled = false`
  в local/user override либо удалить project config вместе с изменением;
- Claude Code: не подтверждать project server либо удалить его entry из
  `.mcp.json` вместе с изменением;
- остановить client session; закрытие stdin штатно завершает stdio process, а
  launcher удаляет каталог копии этой сессии;
- удалить `.artifacts/` и обычные `bin/obj`, если нужна очистка производных
  файлов.

Конфигурация не создаёт listener, credential или внешнее соединение. Editor
adapter оценивается отдельно и не входит в production/runtime dependency graph
domain MCP.

## Dev-only Ivan-MCP для редактора

ADR 0004 принимает Ivan-MCP как доверенный локальный инструмент для тестовой
игры. Это не production dependency и не security sandbox: локальный MCP client
получает широкие editor/source/filesystem/reflection возможности. Не запускайте
его в worktree с секретами или недоверенным кодом.

Установка и запуск с Godot 4.7.1 .NET:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 `
  -Action Install `
  -GodotPath C:\path\to\Godot_v4.7.1-stable_mono_win64_console.exe

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 `
  -Action Open `
  -GodotPath C:\path\to\Godot_v4.7.1-stable_mono_win64_console.exe
```

`Open -Headless` подходит для handshake/tree/log/play проверок, но screenshot
требует обычного оконного редактора. После исправления C# compile error
перезапустите tracked процессы: hot reload Godot может не выгрузить Ivan
assemblies.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 -Action Status
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 -Action Stop
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 -Action Open -Headless
```

Server слушает только `127.0.0.1:29541`/`::1`; cloud и credentials не
используются. Project configs Codex и Claude содержат
`http://127.0.0.1:29541/mcp`, но не запускают server автоматически.

Перед export и для полного отката удалите только candidate-owned локальную
установку:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivan-mcp.ps1 -Action Uninstall
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

`Uninstall` не меняет глобальные настройки и user-scope конфиги. Exact pins,
hashes, лицензии, измерения и принятое исключение security gate находятся в
`MCP_EVALUATION.md` и ADR 0004.

OpenCode с локальной Qwen через Ollama

Проверенная локальная конфигурация: OpenCode `1.18.11`, Ollama `0.32.5` и
`qwen3.6:27b` (`Q4_K_M`, tools/thinking/vision). Project-scoped
`opencode.json` выбирает только provider `ollama`, задаёт модели окно 131 072
токенов, подключает domain MCP и dev-only Ivan-MCP и требует подтверждения для
изменений файлов и shell-команд. MCP tools выключены в обычном coding-контексте:
project-owned domain tools включаются в primary-agent `simulation`, а domain и
широкие editor tools вместе — в primary-agent `godot`; для Ivan-вызовов также
требуется подтверждение. Web, subagent, skill и TODO tools тоже выключены как
необязательные для локального coding loop. Это не только граница риска: полный
OpenCode tool context в измеренном smoke занял 24 163 входных токена и
обрабатывался локальной моделью около десяти минут.

Обычный режим отключает длинный reasoning trace (`reasoningEffort: none`),
потому что на измеренном short smoke модель с включённым thinking сгенерировала
1 712 скрытых reasoning-токенов со скоростью около 8 токенов/с до двухсловного
ответа. Primary-agents `deep` и `godot` используют variant `deep` с высоким
reasoning effort для задач, где эта стоимость оправдана.

OpenCode и coding agents требуют большого контекста. Для Ollama задайте
пользовательскую переменную и перезапустите приложение Ollama:

```powershell
[Environment]::SetEnvironmentVariable("OLLAMA_CONTEXT_LENGTH", "131072", "User")
[Environment]::SetEnvironmentVariable(
  "GODOT4_CONSOLE",
  "C:\path\to\Godot_v4.7.1-stable_mono_win64_console.exe",
  "User")
```

Абсолютный путь хранится только в пользовательском окружении, не в Git. На
Windows с запрещёнными PowerShell scripts запускайте npm shim `opencode.cmd`,
а не `opencode.ps1`:

```powershell
opencode.cmd
```

Перед первой сессией соберите domain MCP и отдельно установите/откройте Ivan по
командам выше. Проверить эффективную конфигурацию можно командами
`opencode.cmd models ollama` и `opencode.cmd mcp list`.

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1
