# Работа с несколькими агентами

Статус: действует  
Дата обновления: 2026-07-26

## Главный принцип

Чат помогает думать, но не хранит каноническое состояние проекта.

Контекст передаётся по цепочке:

```text
Vision / GDD / ADR
        ↓
   GitHub Issue
        ↓
задача агента + отдельная ветка/worktree
        ↓
     Draft PR
        ↓
проверка другим агентом
        ↓
main + актуальная документация
```

Новый агент должен быть способен начать работу из репозитория и Issue без
пересказа старых диалогов.

## Когда использовать текущий чат

Оставаться в одном чате, пока сохраняется одна цель:

- проработка игрового видения и механик;
- уточнение одного Issue;
- реализация и исправления в одном PR;
- диагностика одного воспроизводимого дефекта;
- принятие одного связанного набора решений.

Этот чат можно использовать как **координационный**: обсуждать направление игры,
приоритеты, архитектуру, результаты прототипов и принимать работу.

## Режим ведущего агента

Пользователь может задать направление и явно включить режим ведущего, например:

```text
Веди инициативу по экономическому прототипу.
Сам создавай Issues, делегируй реализацию и research, исправляй обычные дефекты
после независимого review. Возвращайся ко мне только с настоящими развилками.
Merge policy: draft-only.
```

В этом режиме ведущий агент:

1. превращает направление в проверяемые Issues и граф зависимостей;
2. составляет полный task brief и назначает задаче роль, worktree и
   provider-neutral класс модели;
3. запускает независимые задачи параллельно, а зависимые — после их prerequisites;
4. проверяет handoff, diff, тесты и CI с независимым review-субагентом;
5. возвращает обычные дефекты исполнителю, принимает исправления и повторяет
   проверки без участия пользователя;
6. после каждого законченного блока даёт пользователю понятный block report и
   сообщает следующий блок;
7. передаёт пользователю decision brief при настоящей развилке;
8. обновляет канонические документы и закрывает или архивирует завершённые
   задачи.

Настоящей развилкой считается:

- изменение продуктового обещания, scope или приоритета;
- труднообратимая архитектура, формат сохранения или миграция данных;
- новый платный сервис, лицензия, внешний обмен данными или privacy/security
  риск;
- конфликт с принятым ADR либо два сопоставимых варианта с разной долгосрочной
  стоимостью;
- действие, для которого нет полномочий: merge, публикация, секрет, покупка или
  изменение внешней системы.

Не являются развилкой обычная ошибка теста, локальный обратимый выбор
реализации, форматирование, исправление CI или первая неудачная попытка. Их
ведущий агент обрабатывает самостоятельно.

### Отчёт после блока

Блок — законченный проверяемый этап, после которого изменилось состояние
инициативы. Обычно это discovery/план, реализация сквозного куска,
verification/review или интеграция. Отдельный вызов инструмента, один commit или
промежуточный лог блоком не считаются.

После каждого блока ведущий сообщает:

```text
Блок: название и его цель.
Результат: что теперь работает или стало известно.
Проверка: команды, тесты, CI, сценарии и независимый review.
Исправления: какие замечания нашёл review и что было изменено.
Ограничения: что намеренно не входит или ещё не доказано.
Дальше: следующий блок, его результат и зависимости.
Нужно от пользователя: только если возникла настоящая развилка.
```

Block report не должен быть однословным статусом или перечнем файлов. Он
объясняет смысл результата на уровне пользователя. При длинном блоке ведущий
может давать короткие промежуточные статусы, но в конце всё равно публикует
полный отчёт.

Decision brief содержит только:

```text
Контекст: что стало известно.
Варианты: 2–3 реально различающихся пути.
Рекомендация: один путь и почему.
Цена решения: время, риск, деньги или необратимость.
Нужно от пользователя: конкретный выбор или полномочие.
```

### Политика merge

- `draft-only` — значение по умолчанию: ведущий готовит и проверяет draft PR,
  но не merge'ит его без явного разрешения;
- `green-auto-merge` — пользователь заранее разрешает merge обычных PR после
  зелёного CI и независимого review;
- даже при `green-auto-merge` ведущий останавливается перед ADR, изменением
  продуктового scope, зависимостью с новой лицензией, security/privacy
  расширением, платным сервисом и необратимой миграцией.

Политика задаётся для инициативы, а не предполагается из старого чата.

### Review и исправления

Каждый записывающий блок проходит цикл:

```text
implementer → проверки исполнителя → независимый reviewer
            → обычные исправления → повторные проверки → принятие ведущим
```

- reviewer работает read-only в отдельной задаче/субагенте и не использует
  историю рассуждений implementer как доказательство корректности;
- ведущий сверяет результат с Issue, ADR, diff, тестами и наблюдаемым поведением;
- обычные замечания ведущий отправляет implementer или исправляет в отдельной
  изолированной записи, после чего повторяет релевантные проверки;
- обычные исправления и повторная проверка остаются частью исходного блока:
  reviewer и ведущий принимают его итоговый diff, а не создают бесконечную
  цепочку новых блоков;
- новый блок начинается только при новой цели, расширении scope или отдельном
  результате, который можно независимо принять;
- пользователь не выполняет роль тестировщика и не участвует в выборе локального
  исправления;
- при security, необратимой архитектуре, изменении scope или нехватке полномочий
  цикл останавливается и формируется decision brief.

## Когда открывать новую задачу или чат

Открывать новую задачу, если:

- начинается реализация нового Issue;
- работа может идти параллельно с текущей;
- нужен независимый review без влияния истории реализации;
- меняется цель, ветка или набор критериев готовности;
- текущий чат заполнен логами и исследованиями, которые больше не нужны;
- работу принимает другой агент или провайдер.

Обычно один Issue соответствует одной задаче агента и одному draft PR. Маленькие
неразделимые исправления могут объединяться, если у них общие критерии готовности.

## Что дать новому агенту

Не нужно вставлять всю историю чатов. Достаточно:

1. открыть репозиторий из корня;
2. указать ссылку или номер GitHub Issue;
3. убедиться, что Issue содержит полный task brief из следующего раздела;
4. назвать требуемую роль и границы текущего блока;
5. явно потребовать проверку и формат handoff.

Следующие короткие промпты допустимы только поверх Issue, в котором уже заполнен
полный task brief. Если обязательных полей нет, агент сначала возвращает задачу
ведущему на уточнение, а не угадывает scope.

Минимальный стартовый промпт реализации:

```text
Работай по Issue #N в репозитории dungeon-fortress.
Прочитай корневые инструкции агента и документы, связанные из Issue.
Проверь why_now, scope, non-goals, deliverables, acceptance, dependencies,
constraints, verification и handoff. Если поля неполны или противоречат друг
другу — остановись и сообщи ведущему.
Используй отдельную ветку/worktree, реализуй изменение, запусти проверки,
обнови документацию и подготовь draft PR со ссылкой на Issue.
Существенное новое решение сначала оформи как Proposed ADR.
В handoff перечисли результат, доказательства, ограничения, фактическую модель
и следующий шаг.
```

Для исследования без записи:

```text
Исследуй read-only блок из полного brief Issue #N. Ничего не изменяй.
Соблюдай scope/non-goals и escalation triggers.
Верни факты по первичным источникам, варианты, рекомендацию, риски,
воспроизводимый проверочный spike и недостающие доказательства.
```

Для независимого review:

```text
Проведи review PR #N как независимый агент.
Прочитай полный brief связанного Issue и принятые ADR. Проверь итоговый diff,
корректность, регрессии, тесты, детерминизм и документацию.
Верни findings по приоритету с файлами/строками, затем ограничения проверки.
Не исправляй код и не расширяй scope.
```

## Полный task brief

Ссылка на Issue остаётся источником истины, но одной ссылки недостаточно для
запуска агента. Ведущий передаёт краткий самодостаточный brief:

```yaml
title: понятный ожидаемый результат
why_now: зачем блок нужен следующему этапу или продукту
context:
  - принятые решения и относящиеся документы
scope:
  - что агент должен изменить или исследовать
non_goals:
  - что намеренно не входит
deliverables:
  - код, данные, документы, PR или отчёт
acceptance:
  - наблюдаемые критерии готовности
dependencies:
  - prerequisite Issues, версии и внешние инструменты
constraints:
  - безопасность, совместимость, worktree и запреты
verification:
  - обязательные команды и сценарии
handoff:
  - что вернуть ведущему
complexity: low | medium | high | critical
capability_tier: fast | standard | deep | critical-review
reasoning_budget: low | medium | high | xhigh
escalation_triggers:
  - когда остановиться и передать решение ведущему
suggested_models:
  - необязательные примеры доступных моделей
```

Task brief должен позволять новому Codex, Claude Code или локальному агенту
понять не только «что написать», но и зачем это нужно, как доказать результат и
где остановиться. Если Issue уже содержит все поля, prompt может ссылаться на
него и повторять только роль, границы и ожидаемый handoff.

## Provider-neutral выбор модели

Задача описывает необходимую способность, а не обязательного провайдера.
Перед запуском ведущий добавляет в task brief:

```yaml
complexity: low | medium | high | critical
capability_tier: fast | standard | deep | critical-review
reasoning_budget: low | medium | high | xhigh
escalation_triggers:
  - условие, при котором нужен более сильный класс или решение пользователя
suggested_models:
  - необязательные актуальные примеры
```

Класс определяется по пяти признакам: неоднозначность требований, ширина
изменений, трудность проверки, цена ошибки и обратимость решения. Используется
самый лёгкий класс, который надёжно закрывает критерии готовности.

| Класс | Для чего | Актуальные примеры, не требование |
|---|---|---|
| `fast` | Извлечение, классификация, шаблонное преобразование, короткий read-only scan | OpenAI GPT-5.6 Luna `low/medium`; быстрый Claude или локальный аналог |
| `standard` | Обычная реализация с ясными критериями, тесты, документация, широкое чтение | OpenAI GPT-5.6 Terra `medium/high`; сопоставимый Claude или локальный coding model |
| `deep` | Неоднозначная архитектура, новая интеграционная граница, сложная отладка | OpenAI GPT-5.6 Sol `high`; сопоставимая сильная модель другого провайдера |
| `critical-review` | Security, миграции, труднообратимый ADR, независимое review дорогого изменения | OpenAI GPT-5.6 Sol `xhigh`; сопоставимая top-tier модель |

Названия моделей быстро устаревают и проверяются по `TECH_RADAR.md`. Агент может
выбрать доступный эквивалент того же класса. Конкретная модель и фактический
reasoning budget фиксируются в handoff для оценки качества, времени и стоимости.

Правила маршрутизации:

- research и большие read-only обзоры начинают с `fast` или `standard`;
- хорошо описанная реализация начинает со `standard`;
- ведущий, сложный implementer и независимый reviewer используют `deep` только
  там, где нужны суждение и проверка нескольких гипотез;
- `critical-review` не является дефолтом и включается по высокой цене ошибки;
- уровень повышается после двух содержательных неудач, обнаружения скрытой
  архитектурной границы либо срабатывания явного `escalation_trigger`;
- повторный review обычной локальной поправки может выполняться более дешёвым
  классом, чем первоначальное исследование;
- независимый reviewer не должен быть слабее класса, необходимого для понимания
  риска проверяемого изменения.

## Codex

- Общие инструкции автоматически читаются из корневого `AGENTS.md`.
- Репозиторные настройки Codex при необходимости хранятся в
  `.codex/config.toml`.
- Подагенты полезны для независимого исследования, тестов, анализа логов и
  review. Записывающие подзадачи должны иметь непересекающиеся области или
  отдельные worktree.
- Отдельная пользовательская задача предпочтительна, если работа имеет свой
  Issue, ветку, PR или требует последующего диалога.

## Claude Code

- Корневой `CLAUDE.md` импортирует `AGENTS.md`, поэтому правила не дублируются.
- Локальные предпочтения хранятся в `CLAUDE.local.md` или
  `.claude/settings.local.json` и не коммитятся.
- Для параллельных записывающих сессий используется `claude --worktree <name>`
  либо worktree-изоляция подагента.
- Автоматическая память Claude не является источником истины. Полезное знание
  переносится в Markdown, Issue, ADR или PR.
- Общая MCP-конфигурация Claude появится в `.mcp.json`, когда будет реализован и
  проверен Agent Bridge.
- Координационная сессия начинается командой `/coord`
  (`.claude/commands/coord.md`): она собирает состояние репозитория, разбирает
  coordination inbox и выдаёт отчёт владельцу. Команда коммитится как адаптер и
  не ослабляет правила `AGENTS.md`.

## Coordination inbox

Постоянного чата управления в проекте нет намеренно: контекст диалога
сжимается, а закрытая история сессии не является источником истины.

Роль постоянного входа выполняет долгоживущий Issue
[#33](https://github.com/anshushunov/dungeon-fortress/issues/33). Владелец
пишет туда сырые идеи, вопросы и наблюдения после playtest в любой момент и в
любой формулировке. Координационная сессия начинается с чтения входящих и
разбирает каждую запись в один исход: Issue, ADR или раздел документа, ссылку
на уже принятое решение, отсрочку до названного decision gate либо
мотивированный отказ.

Запись становится решением только после переноса в документ, ADR или Issue.
Сам Issue не закрывается и не используется как backlog: приоритеты живут в
roadmap.

## Другие облачные и локальные агенты

Клиент должен:

- прочитать `AGENTS.md`;
- получить Issue и рабочую копию;
- уметь запустить те же CLI-команды сборки и тестов;
- использовать отдельную ветку/worktree для записи;
- оставить стандартный handoff и draft PR.

Если клиент не поддерживает `AGENTS.md` автоматически, путь к файлу указывается
в стартовом промпте. Клиентская память и закрытая история сессии не заменяют
документацию проекта.

## Параллельная работа

Безопасно распараллеливать:

- исследование разных вариантов;
- чтение разных частей кодовой базы;
- тестирование и профилирование готовой ветки;
- review по независимым направлениям;
- генерацию вариантов арта в отдельные каталоги кандидатов.

Осторожно распараллеливать:

- изменения одной модели данных;
- сцены и ресурсы, которые сохраняет один редактор;
- файлы проекта движка;
- миграции форматов и зависимостей;
- интеграцию нескольких ещё не принятых ADR.

Правила записи:

- одна активная записывающая задача — одна ветка и один worktree;
- два агента не работают одновременно в одной рабочей копии;
- владелец Issue указывается до начала параллельной реализации;
- ветка именуется `agent/<issue>-<slug>`; допустима автоматически созданная
  worktree-ветка, если PR явно связан с Issue;
- интеграцию выполняет отдельный агент или координационный чат после review.

## Handoff

В конце задачи агент оставляет в PR или Issue:

- достигнутый результат;
- изменённые системы и файлы;
- выполненные команды и результаты проверок;
- seed/сценарий воспроизведения, если применимо;
- принятые допущения;
- известные риски и незавершённую работу;
- новые или обновлённые ADR и документы;
- использованные роль, capability tier, модель и reasoning budget;
- точный следующий шаг.

Фраза «готово» без проверок и ссылок не является handoff.

## Provider-neutral Agent Bridge

Игровая автоматизация не зависит от Codex, Claude или конкретного MCP-плагина:

```text
Simulation / Game diagnostic API
              ↓
       CLI или локальный HTTP
              ↓
       стандартный MCP server
       ↙        ↓         ↘
    Codex   Claude Code   local agents
```

Доменные команды, JSON-схемы, ошибки и сценарии тестируются без MCP. Для клиентов
коммитятся только адаптеры и безопасные конфигурации:

- `.codex/config.toml` — проектные настройки Codex;
- `.mcp.json` — project-scoped MCP для Claude Code;
- примеры конфигурации других клиентов по мере появления необходимости.

Секреты, токены и абсолютные пути конкретной машины остаются в пользовательском
или local scope.
