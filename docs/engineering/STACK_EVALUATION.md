# Сравнение стека первого прототипа

Статус: исследование  
Дата проверки источников: 2026-07-26

## Критерии

В порядке важности для текущей стадии:

1. короткий цикл «изменение → автоматическая проверка → запуск → наблюдение»;
2. качественный 2D и интерфейс для насыщенной симуляции;
3. возможность отделить детерминированную симуляцию от кадров и представления;
4. управление редактором и рантаймом агентами;
5. профилирование и путь к сотням или тысячам участников;
6. стоимость и отсутствие лишних организационных зависимостей.

## Варианты

| Вариант | Сильные стороны | Основные риски | Вывод |
|---|---|---|---|
| Godot 4.7.1 .NET + C# | Быстрый и лёгкий редактор, специализированный 2D-движок, текстовые сцены, CLI/headless, MIT, чистая интеграция с .NET | MCP-экосистема моложе Unity; встроенный C#-редактор минимален; нет официального универсального game-test framework | Предпочтительный стек для прототипа |
| Unity 6.3 LTS + C# | Зрелый редактор и экосистема, Test Framework, Entities/DOTS, наиболее зрелые MCP-плагины | Более тяжёлый цикл редактора и импорта; больше служебного состояния проекта; проприетарная зависимость | Запасной вариант, если Godot automation окажется недостаточной |
| Bevy 0.19 + Rust | Data-oriented ECS, производительность, code-first и удобный headless-контур | Rust и компиляция замедляют исследовательские итерации; слабее визуальный редактор и MCP-контур | Не брать основным движком на стадии поиска игры |
| Собственный движок | Полный контроль над симуляцией и инструментами | Почти всё время уйдёт на инфраструктуру вместо игрового цикла | Не рассматривать до доказанной необходимости |

## Рекомендация

Провести первый технический и игровой прототип на:

- **Godot 4.7.1 .NET edition**;
- **C# и .NET 8**;
- **2D сверху** как самый дешёвый способ проверить читаемость механик;
- чистая C#-библиотека симуляции без зависимости от `Godot.*`;
- тонкий слой Godot, преобразующий ввод игрока в команды симуляции и состояние
  симуляции в представление;
- обычные `dotnet test` для большей части правил;
- небольшое число headless/integration smoke-тестов через Godot.

Изометрическое представление проверяется позже заменой слоя визуализации. Модель
мира не должна использовать экранные координаты как доменные.

Версии bootstrap-spike закреплены как .NET SDK 8.0.423 и Godot 4.7.1 .NET.
Godot не обязан находиться в `PATH`: локальные скрипты также поддерживают
`GODOT4_CONSOLE` и явный override. Настройка описана в
`ENVIRONMENT_SETUP.md`; абсолютный путь конкретной машины в репозитории не
хранится.

## Предлагаемая структура

```text
src/
  DungeonFortress.Simulation/  # время, сущности, экономика, команды, события
  DungeonFortress.Game/        # проект Godot и адаптер представления
tests/
  DungeonFortress.Simulation.Tests/
  DungeonFortress.Scenarios/
tools/
  DungeonFortress.AgentBridge/ # CLI/API, позднее MCP-адаптер
```

Состояние симуляции не хранится в узлах Godot. Узлы отображают проекции состояния
и могут быть уничтожены или пересозданы без потери доменной информации.

## Стратегия симуляции

Не начинать с универсальной ECS. Для первых прототипов достаточно:

- стабильных идентификаторов существ;
- фиксированного дискретного времени;
- очереди команд и доменных событий;
- систем, обрабатывающих коллекции данных пакетно;
- нескольких уровней детализации по частоте и полноте обновления;
- снимка состояния и журнала команд для воспроизведения.

Оптимизация начинается с сценария-нагрузки и профиля. Если обычная C#-модель не
достигает нужного масштаба, данные горячих систем можно перевести в
data-oriented layout без смены движка и продукта.

## MCP и агентская отладка

Готовый MCP-плагин полезен для сцены, ресурсов, запуска и скриншотов, но не знает
смысла нашей симуляции. Поэтому нужны два слоя:

1. **Универсальный адаптер движка** — открыть сцену, запустить игру, прочитать
   ошибки, получить скриншот, проверить импорт.
2. **Наш Agent Bridge** — установить seed, выполнить N тиков, отправить игровую
   команду, получить JSON-снимок, проверить инварианты и выгрузить профиль.

Для Godot есть как минимум два перспективных направления для короткого spike:

- `IvanMurzak/Godot-MCP`: C#-аддон, 42 встроенных инструмента, собственные
  runtime tools, сбор ошибок, локальный/self-hosted режим;
- `slangwald/godot-mcp`: простой Python/TCP-мост с деревом сцены, запуском,
  скриншотами и вводом.

Их нельзя считать фундаментом игры до проверки совместимости, восстановления
после ошибок компиляции и безопасной параллельной работы. Доменные инструменты
должны оставаться доступными через CLI/API без MCP.

## Проверочный spike перед принятием решения

За один короткий эксперимент агент должен суметь:

1. собрать чистую библиотеку симуляции и выполнить тесты;
2. запустить Godot headless и обычным окном;
3. создать или изменить тестовую сцену;
4. запустить 1 000 агрегированных существ на 10 000 тиков с фиксированным seed;
5. получить JSON-снимок состояния и повторить тот же результат;
6. прочитать ошибки рантайма и сделать скриншот через MCP;
7. восстановить рабочее состояние после намеренно внесённой ошибки C#.

Если пункты 2, 3, 6 или 7 нестабильны, повторить тот же spike на Unity 6.3 LTS и
сравнить полное время итерации, а не только число MCP-инструментов.

### Результат bootstrap-spike

Issue #3 проверяет engine-independent контур без выбора или установки MCP.
Реализованы пункты 1–5:

- pure C#/.NET 8 simulation core не ссылается на `Godot.*`;
- Godot 4.7.1 .NET запускает ту же модель headless и в обычном окне;
- сцена остаётся тонкой проекцией канонического состояния;
- runner принимает seed, число агентов, число fixed ticks и JSON-команды;
- canonical JSON строится с фиксированным порядком полей и получает SHA-256.

Локальная полная проверка 2026-07-26 с seed `424242` дала:

- 32 агента × 256 тиков:
  `e65273aa102f4db01d2cf64ecc48b1556700544f5da0fe7c19378d1d089b6f6f`;
- seed `424243`:
  `cf6f51cc21481f8db9dfb28a0e34ed7cd6a03e12caa9c72a93a854b932afddd2`;
- 1 000 агентов × 10 000 тиков:
  `7ec0f2d64522e96e8fd80773d8a9e7e89ced643ab212aaa2741ea40081a85045`,
  два последовательных запуска заняли 222,431 и 226,973 мс.

Время — измерение harness на одной машине, а не performance target. Пункты 6–7
относятся к отдельному MCP-spike, поэтому ADR 0003 остаётся `Proposed`.

Review visible smoke также подтвердил, что runtime нельзя наследовать длинный
NuGet `APPDATA` из worktree: Windows path к GLES3 shader cache достигал 255
символов и Godot возвращал ошибку создания каталога. Скрипты теперь используют
короткий отдельный runtime profile и считают любую строку `ERROR:` провалом даже
при process exit code 0. Детали и upstream-ссылки находятся в
`ENVIRONMENT_SETUP.md`.
