# Темп разработки

Процессные правила проекта: темп, review, параллелизм, автономия
координатора. Раздел вынесен из [`ROADMAP.md`](../product/ROADMAP.md), где он
занимал 76 КБ продуктового документа; ссылки на «правило N» ведут сюда.
Решения владельца, которыми эти правила приняты, —
[`GATE_DECISIONS.md`](../product/GATE_DECISIONS.md).

Направление владельца от 2026-07-31 — **time to market**. Правила 1–7 приняты в
первой координационной сессии дня; 8–10 — во второй (из находок блока «паника
как решение существа» и хода самой сессии); 11–15 и сжатие калибровки —
**в третьей**, Issue [#122](https://github.com/anshushunov/dungeon-fortress/issues/122),
в ответ на PR #121 (563k, восемь запусков, ни одного нового игрового поведения
— разбор в самой Issue, не копируется сюда, правило 8). С этой третьей сессии
действует **мораторий на новую процессную документацию** — правило 11.

**Правила 16 и 17 приняты позже**, решениями владельца 2026-08-01 в блоке боя,
**правило 18 — решением владельца 2026-08-02** (снято правилом 24 в тот же
день), **правила 19–23 — решением владельца 2026-08-02 об экономии токенов**,
**правило 24 — решением владельца 2026-08-02 об автономии координатора**,
**правила 25–28 — решениями владельца 2026-08-02**: 25 и 26 приняты по ходу
блока #171/#77/#165, 27 и 28 вместе с поправкой к правилу 19 — во второй
координационной сессии того же дня; все живут в отдельных секциях ниже.
Преамбула датирует 2026-07-31 только правила 1–15.

Правило этого раздела действует и там, где расходится с буквой принятого ADR
0014 или 0017: при расхождении приоритет у правила, а не у ADR. Это общее
правило — разрешение на расхождение не держится на поимённом списке, который
надо вспомнить; расхождение при этом обязано быть названо в тексте самого
правила (строка «ослабляет ADR 001X» в его теле). На сегодня ADR 0014 и 0017
ослабляют правила 2, 5, 7, 24, 28 и 29; число получено и сверяется командой ниже
(правило 8).

Команда-проверка: правило раздела ослабляет ADR, если в его тексте есть
«ослабляет» и номер ADR 0014 или 0017.

```bash
awk '
/^### Темп разработки/ { s=1; next }
s && /^### / { s=0 }
s && /^\*\*[0-9]+\./ { if (r!="" && blk ~ /[Оо]слабл/ && blk ~ /ADR 001[47]/) print r; r=$0; sub(/^\*\*/,"",r); r=substr(r,1,index(r,".")-1); blk=""; next }
s { blk = blk " " $0 }
END { if (r!="" && blk ~ /[Оо]слабл/ && blk ~ /ADR 001[47]/) print r }
' docs/product/ROADMAP.md | sort -un
```

Вывод: `2 5 7 24 28 29` — шесть правил, число совпадает с преамбулой.

**1. В блоке обязателен gameplay-слайс.** Обеспечивающие задачи занимают
оставшиеся слоты, а не заменяют содержание блока. Прежняя форма правила «не
подменяем игру подготовкой» звучала как «не два обеспечивающих блока подряд» —
она соблюдалась и всё равно допускала блок, из которого владелец не получал ни
одной фичи. Новая форма: **в каждом блоке хотя бы одна фича.**

**2. До двух gameplay-слайсов одновременно, и считаются вопросы, а не слайсы.**
Ограничение защищает интерпретируемость playtest, а не стоимость. Второй слайс
открывается, только если у слайсов разные вопросы playtest, нет общей балансной
поверхности и владелец до игры знает, что смотреть в каждом. Балансные слайсы не
параллелятся никогда; три и более не допускаются ни при каком бюджете.

Ослабляет «ровно 1» из [ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §1,
§3 и [ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §1; их
основание — интерпретируемость playtest — сохранено как условие правила. Откат:
владелец не смог развести эффекты двух слайсов → снова один слайс, запись в
журнал.

**3. Глубина review назначается заранее и по названным признакам**, а не
выбирается по ходу: **маркеры риска** (детерминизм, канонический снапшот,
design-контракт, словарь команд, продуктовое обещание, расширение полномочий
агента) и **объём контекста, который придётся поднять**, чтобы проверить
утверждения изменения. **Присутствие любого маркера означает полную
глубину** — review самостоятельно переспрашивает проверки, а не
ограничивается критериями готовности и diff'ом. **Занижать глубину за
отсутствие кода и за малый diff запрещено** — проверено на PR #98 (вывод 1
калибровки [`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md)):
цену задаёт объём поднимаемого контекста, а не класс изменения.

Независимый review остаётся обязательным для **каждого** PR
([ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §4), включая
правку статуса в этом документе. Второй и последующие круги ведёт **тот же**
возобновлённый агент (вывод 2 калибровки) — и это же теперь ограничено потолком
кругов, правило 12.

**4. Находка review становится Issue только при наблюдаемом последствии**
(для игрока либо для реально гоняемой проверки); без последствия — запись в
[`DEBT_LEDGER.md`](DEBT_LEDGER.md), слота в очереди не получает.
Основание: у review-порождённых задач нет продуктового сигнала приоритета —
замер на 2026-07-31 нашёл, что review был крупнейшим источником открытых
non-gameplay задач, но не большинством (4 из 9: [#49](https://github.com/anshushunov/dungeon-fortress/issues/49),
[#74](https://github.com/anshushunov/dungeon-fortress/issues/74),
[#106](https://github.com/anshushunov/dungeon-fortress/issues/106),
[#109](https://github.com/anshushunov/dungeon-fortress/issues/109); остальные —
исполнитель и playtest владельца). **Замер устарел и оставлен как
свидетельство на дату, а не как текущее состояние**: часть перечисленных
Issue с тех пор закрыта. Перечитывать список нельзя без проверки —
`gh issue list --state all --json number,state` — правило 8. Правило держится
на решении владельца, подпёртом этим наблюдением, а не на измерении,
доказывающем порог.

**Исход предлагает review, а не координатор единолично**: координатор
соглашается либо повышает до Issue, понизить против предложения review не
может — симметрично правилу 7. Не касается возврата на доработку (критерий
готовности не выполнен) и ложного утверждения документа о репозитории — это
дефект самого документа, а не находка для реестра. Откат: запись реестра
всплыла видимым дефектом → правило пересматривается, запись в журнал.

**5. Именованный регион разрешён в любом файле.**
[ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §3 ограничивал
регион двумя файлами (`Main.cs`, `verify.ps1`); правило ослабляет
ADR 0017 §3 — перечень упразднён, потому что он не покрывал узлы,
в которые сходятся gameplay-слайсы (`PrototypeWorld.cs`,
`PROTOTYPE_01_PREPARE_FOR_RAID.md`). **Все четыре условия ADR 0017 §3
сохраняются полностью**: перечисление членов с обеих сторон (не описание вида
«`_Draw` и всё, что он вызывает»), назван владелец остатка, порядок merge в
брифах, rebase на координаторе. Если хотя бы один член нужен обеим задачам —
разделения нет, задачи идут последовательно. Откат: rebase региона потребовал
переписывания, а не слияния → правило возвращается к перечню.

**6. Постоянная дорожка визуала.** В каждом блоке — одна задача класса `art`
(исполняет Codex, [ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §8);
подключение ассета — отдельный шаг класса `support`. До 2026-08-02 из этого
следовало, что дорожка стоит один слот записывающего агента на блок; **потолок
снят правилом 28**, и слотов больше нет. Подключение при этом осталось
записывающей задачей и **владеет своими файлами по партиции**: «дорожка визуала
ничего не отнимает» по-прежнему неверно — она отнимает файлы, а не слот.

**7. Одобрение прикрепляется к решению, а не к каждому PR.** PR, только
исполняющий уже принятое владельцем решение, мержится без второй просьбы при
зелёном CI, `verify.ps1`, независимом review и Issue с наблюдаемыми критериями
готовности — независимо от класса задачи. ~~Владельцу по-прежнему возвращается:
выход за пределы одобренного (включая изменение продуктового обещания или
scope), новое решение, труднообратимое изменение, новый риск
безопасности/лицензии/приватности/расходов, конфликт с принятым ADR, ADR с
непринятым решением, нехватка полномочий — список совпадает с эскалациями
`AGENTS.md` плюс два пункта, специфичных для PR.~~ **Этот список заменён
2026-08-02** решением владельца (PR #181): владельцу возвращается то, что
попадает в три категории [правила 24](#автономия-координатора-2026-08-02), плюс
PR, которому независимый review отказал в квалификации под настоящее правило.
Прежний текст оставлен зачёркнутым как протокол; условия merge в первой фразе
правила 7 не тронуты. **Квалификацию PR под правило
подтверждает независимый review, а не координатор единолично** (симметрично
правилу 4): путь правила 7 открыт любому классу, включая `gameplay` и
`decision`, и снимает условия §5 про контракт/словарь/ADR/продуктовые
документы — но не условие «Issue с критериями», перенесённое из §5 без
снятия. PR `decision` без Issue правилу 7 не удовлетворяет и требует
`MERGE #N`. **Gate не отменяется**: gameplay-слайс по-прежнему получает
playtest и `CONTINUE/ADJUST/PROMOTE/DEFER/STOP`. Ослабляет
[ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §5 и §7: класс
задачи перестаёт быть условием пути правила 7 (путь §5 не меняется). Откат:
смерженный без второй просьбы PR вышел за пределы одобренного → правило
отменяется, запись в журнал.

**8. Правило факта: число, состояние Issue и имя коммита не попадают в документ
копированием.** Пишешь число — **называешь команду**, которой его получил, либо
ссылаешься на **единственное место**, где оно записано. **Способ проверки
уточнён правилом 33** (решение владельца 2026-08-04): правка, меняющая состояние
задачи, проверяется перечислением всех вхождений её номера, а не прогоном по
метке статуса. Копия без источника
расходится с источником молча и живёт дальше как факт — измерено 2026-07-31,
три расшедшиеся копии за один день, разбор в PR #112 и #118. Закрывается
удалением копии, а не подновлением числа; действует на числа, состояние Issue
и имена коммитов одинаково во всех документах репозитория.

**9. Правило мутации каждой половины: новая проверка не считается сделанной,
пока не показано, что она краснеет при откате каждой части изменения.** Мутант
ставится на **каждую** половину правки, а не на правку целиком — проверка,
краснеющая только на полном откате, доказывает покрытие хотя бы одной половины
и ничего не говорит о второй. Выведено на #101, где ровно так и было. С
2026-08-02 сужено правилом 21: где мутант обязателен, а где назначается брифом,
сказано там.

**10. Записывающий агент выносит наружу то, что дорого получить заново.**
Коммит на каждом рубеже, а не один в конце; измерение — в файл
`evidence/<issue>-<что>.json` вместе с командой в момент получения (операционная
форма правила 8); незавершённая работа названа в сообщении коммита. Рубежи
называются в брифе — поле `checkpoints`
[`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md). Правила
8–10 бесплатны — строки в брифе и коммите, не инфраструктура. Откат для всех
трёх: правило дороже находок, которые приносит → отменяется, запись в журнал.

**Бухгалтерию Issue ведёт координатор**, закрывает выполненные и заводит новые
по находкам review без отдельного вопроса владельцу (правило 4).

**Процессные правила живут здесь, ADR — для другого.** ADR остаётся формой для
существенного продуктового, архитектурного и технологического решения и для
контракта (`TECH_RADAR.md` — отдельно для движка/SDK/MCP/генеративного
инструмента). Процессное правило — темп, глубина review, параллелизм, порядок
работы — записывается в этот раздел, а не ADR: пересмотр стоит правки абзаца,
а не нового ADR. Принятые ADR этим разделом не отменяются; где правило расходится
с их буквой, действует правило раздела (преамбула), и расхождения названы
в тексте правил 2, 5, 7, 24, 28 и 29.

## Мораторий на процессную документацию и сжатие калибровки (третья сессия 2026-07-31)

В ответ на измерение: PR #121 стоил **563k** за восемь последовательных
запусков агентов и не дал игре ни одного нового поведения — разбор Issue
[#122](https://github.com/anshushunov/dungeon-fortress/issues/122).

**11. Мораторий на процессную документацию.** Новых ADR не появляется, кроме
труднообратимых решений; новых процессных правил не появляется; этот документ
перестаёт носить эссе с обоснованиями — обоснование правила сжимается до одной
фразы со ссылкой, само правило остаётся целиком (применено к правилам 1–10
выше). **Мораторий действует с 2026-07-31 и отменяется только явным решением
владельца.** Ирония названа прямо, а не спрятана: мораторий на новые
процессные правила введён пятью новыми процессными правилами (11–15) — они
последние **в своей сессии**, и мораторий действует с момента их записи.
Правила 16 и 17 приняты позже отдельными решениями владельца — той формой отмены,
которую этот же мораторий для себя и предусматривает.

**12. Потолок кругов review: один разбор плюс один подтверждающий.** Находка
после второго круга становится Issue или записью в
[`DEBT_LEDGER.md`](DEBT_LEDGER.md), если не ломает критерий
готовности своей Issue. Инвариант «независимый review обязателен для каждого
PR» ([ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §4) не
трогается; правило 3 «второй круг ведёт тот же возобновлённый агент» остаётся —
он просто становится последним.

**13. Бриф самодостаточен.** Бриф несёт выдержки, а не ссылки; обязательное
чтение содержит только то, что бриф физически не может нести. Issue
[#33](https://github.com/anshushunov/dungeon-fortress/issues/33) уходит из
обязательного чтения исполнителей — это inbox координатора, а не постановка.

**14. Маршрутизация модели и effort по классу круга обязательна.** Первый
разбор review и балансный слайс — сильная модель и высокий effort; круги
доработки, подтверждения и механические правки — дешёвая модель и низкий
effort. **С 2026-08-02 первый разбор review из этой строки изъят правилом 27:**
его дефолт — дешёвая модель, сильная назначается по маркерам риска правила 3.
Балансный слайс и круги доработки читаются здесь без изменений. **«Дешёвая»
уточнена правилом 34 (2026-08-07): это средняя модель (Sonnet 5), не младшая —
младшего класса в проекте нет.** Таблица
классов — раздел «Provider-neutral выбор модели»
[`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md); правило там
уже было описано и не применялось ни разу — теперь оно обязательно к
назначению в брифе.

**Дефолтный `reasoning_budget` — `high`** (решение владельца 2026-08-01, см.
журнал). Дефолт действует **в остатке**: там, где это правило, таблица классов
или раздел «Точность» предписывают дешёвый бюджет, действуют они. `xhigh` —
только суперсложной задаче и с названной в брифе причиной. Оговорка: круг
подтверждения ведёт возобновлённый агент, effort у которого сменить нельзя,
поэтому дешевизна такого круга держится на сохранённом контексте, а не на
понижении бюджета.

**15. Проверка утверждений в review становится выборочной.** Требование
«проверить командой каждое утверждение о репозитории, не выборочно» снимается:
правило 8 закрывает эту дыру на стороне автора. Выборка обязана покрывать
несущие утверждения, а не первые попавшиеся — именно полная проверка поймала
самую тяжёлую находку PR #121.

Плюс разовая чистка: **калибровка сжата** до пяти строк, покрывающих разные
виды работы, и трёх выводов — раздел «Калибровка»
[`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md); полная
таблица и все одиннадцать выводов —
[`CALIBRATION_HISTORY.md`](archive/CALIBRATION_HISTORY.md), ни
одно число не потеряно.

## Ожидания и владение рабочей копией (блок боя, 2026-08-01)

Два правила приняты **явными решениями владельца** по ходу блока боя — это та
форма отмены моратория, которую правило 11 для себя же и предусматривает.
Правила 11–15 остаются последними правилами своей сессии; эти две — следующей.

**16. Задача выдаётся с саммари «До → Меняем → После».** **Решение владельца
2026-08-01.** Называя задачу, координатор одной строкой на каждый пункт говорит,
что в игре или в репозитории есть сейчас, что задача меняет и что владелец
получит на выходе. Правило про ожидания, а не про формат: без строки «до»
владелец не может оценить, стоит ли изменение своей цены, а без строки «после» —
понять, что проверять на playtest. **Цена названа:** три строки в каждой выдаче
задачи и то, что координатор обязан знать состояние «до» **до** запуска агента, а
не узнавать его из handoff.

**17. Корневая рабочая копия принадлежит координационной сессии.** **Решение
владельца 2026-08-01**, а не вывод координатора из удобного случая. Записывающий
агент любого инструмента, включая Codex, работает в своём worktree и не
переключает ветку в корне. Правило, команда и измеренная причина — раздел
«Работа нескольких агентов» [`AGENTS.md`](../../AGENTS.md); коротко: независимый
review чужого PR нашёл корневую копию не на той ветке и не мог отличить это от
постороннего вмешательства. **Цена названа:** обязательный лишний worktree на
каждую записывающую задачу, чей первый прогон дороже
([`ENVIRONMENT_SETUP.md`](ENVIRONMENT_SETUP.md)); правило снимает
не неудобство, а потерю доверия проверяющего к дереву, которое он проверяет.

## ~~Запуск агентов идёт по команде владельца (2026-08-02)~~ — снято 2026-08-02

**Правило 18 снято решением владельца 2026-08-02, PR #181** — тем самым
отдельным решением владельца, которого требовал последний абзац самого правила.
Действует [правило 24](#автономия-координатора-2026-08-02). Текст ниже сохранён
как протокол: он объясняет, что именно снято и какой ценой правило вводилось.

~~**18. Координатор не запускает агентов без команды владельца.**~~ **Решение
владельца 2026-08-02**, принято вместе с разовым третьим кругом по PR #174.
Правило касается **всех** агентов — записывающих, review и разведки, — и
относится к запуску, а не к составу блока: декомпозицию, партицию, оценку и
брифы координатор по-прежнему готовит сам и показывает владельцу, но команда
«запускай» принадлежит владельцу. Возобновление уже работавшего агента новым
запуском не является: круг, разрешённый владельцем, доводится до конца тем же
агентом без отдельной команды.

**Цена названа, и она в темпе.** Правило вставляет ожидание владельца между
готовым брифом и работой, то есть прямо противоречит направлению time to market
из преамбулы этого раздела. Принято сознательно: расход блока измеряется
миллионами токенов, счётчик харнесса агентам не виден — это назвали сами агенты
блока боя, единственное место записи — handoff в
[#33](https://github.com/anshushunov/dungeon-fortress/issues/33) от 2026-08-01, —
и до 2026-08-02 единственным, кто решал, тратить ли
их, был координатор — то есть сторона, чей блок этими тратами и собирается.

**Условия отката у этого правила нет.** Оно ограничивает полномочия
координатора, поэтому сузить или снять его может только владелец отдельным
решением — координатор не вправе сделать это по собственному наблюдению, как бы
это наблюдение ни выглядело.

## Экономия токенов (решения владельца 2026-08-02)

Пять правил приняты одним решением владельца — формой отмены моратория
(правило 11), которую он для себя предусматривает. Повод — разбор расхода:
фиксированная цена процесса вокруг задачи сравнялась с ценой самой задачи, и
крупнейшая её часть — полный подъём контекста новым review-агентом на каждом
PR (вывод 1 калибровки
[`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md)). Тем же
решением потолок записывающих возвращён к **двум** по встроенному условию
[ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §5 — владелец
объявил бюджет дефицитным; это исполнение записанного отката, а не новое
правило. **Этот возврат отменён в тот же день** решением владельца о правиле 28
(секция «Облегчение review и снятие потолка» ниже); абзац оставлен как протокол
того, чем потолок обосновывался, пока действовал.

**19. Возобновляемый reviewer вместо нового на каждый PR.** **Редакция
2026-08-02 — единица возобновления область, а не блок; поправка и её основание —
в конце правила.** Ниже сначала исходная редакция «один reviewer на блок», как
она была принята, потому что поправка меняет только единицу и ничего больше.
Первый PR блока reviewer разбирает с полным подъёмом контекста; каждый
следующий PR и каждый следующий круг ведёт **тот же возобновлённый агент**.
Инвариант [ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §4 не
тронут: каждый PR получает независимый review, и reviewer не является
исполнителем ни одного PR блока. Основание — вывод 2 калибровки: дешёвый
review — это сохранённый контекст, а не уменьшенная глубина. При переполнении
контекста блок получает нового reviewer с полным подъёмом, и смена называется
в блок-отчёте. Механика — «Review и исправления»
[`MULTI_AGENT_WORKFLOW.md`](MULTI_AGENT_WORKFLOW.md). Откат:
блочный reviewer пропустил регресс, который нашёл бы свежий агент, →
правило пересматривается, запись в журнал.

**Поправка 2026-08-02: reviewer возобновляется на область, а не на блок.**
**Решение владельца** той же сессии, что правила 27 и 28. При снятом потолке
(правило 28) один блочный reviewer становится очередью: merge пятого PR ждёт
review первых четырёх. Вместо одного блочного действуют **возобновляемые
reviewer по областям, и областей три**: `симуляция + контракт`,
`представление`, `tooling + docs`. Каждый поднимает контекст своей области один
раз и переиспользует его между PR этой области. Основание — вывод 1 калибровки:
цену review задаёт объём поднимаемого контекста, а контекст области меньше
контекста блока, поэтому схема и дешевле, и масштабируется линейно. **Цена
названа:** если в блоке идут все три области, база платится трижды вместо
одного раза; принято сознательно как плата за пропускную способность.
Сохраняется без изменений: reviewer read-only и не публикует ничего
(правило 26), вердикт переносит координатор; reviewer не является исполнителем
ни одного PR, который проверяет; исход по находке называет review (правило 4);
квалификацию под правило 7 подтверждает review.

**20. Вложенные сабагенты запрещены по умолчанию.** Implementer работает один.
Исключение — один read-only scout, названный в брифе явной строкой, с одним
конкретным вопросом и списком файлов. Основание — оговорка калибровки: расход
вложенного субагента не виден счётчику харнесса и складывается с расходом
основного (измерение 2026-08-01 там же).

**21. Мутация каждой половины (правило 9) сужена.** Мутант обязателен для
проверок симуляции, детерминизма и контракта; для слоя представления и
документации — по назначению в брифе, а не по умолчанию. **Уточнено правилом 32
(решение владельца 2026-08-04):** единица назначения — не половина изменения, а
**утверждение, которое проверка делает**; мутант «убрать вызов» и мутант
«перевернуть знак» опровергают разные утверждения, и первый не подразумевает
второго.

**22. Полный `verify.ps1` — один раз на PR**: на финальном состоянии перед
review. Промежуточные круги гоняют таргетные тесты, названные в брифе.
Красный полный прогон после доработки перегоняется — это не «второй раз».

**23. Выдача одиночной задачи идёт лёгким режимом.** Полный сбор состояния
(`/coord` — открытые PR с обсуждениями, Issues, inbox #33, реестр долга) —
на границе блока, после playtest и при развилке. Для выдачи одной задачи по
уже принятому решению координатор читает `NOW`, Issue задачи и названные в ней
документы — адаптер `.claude/commands/task.md`.

## Автономия координатора (2026-08-02)

**24. Координатор сам запускает агентов и сам мержит PR.** **Решение владельца
2026-08-02**, той же формой отмены моратория (правило 11), которую он для себя
предусматривает. Наверх выносятся **блокеры, архитектурные решения и
геймплейные решения** — формулировка владельца, и координатор не расширяет её
своим списком. Правило касается агентов всех видов: записывающих, review и
разведки.

**Эти три категории заменяют семипунктовый список правила 7, а не дополняют
его.** **Решение владельца 2026-08-02**, отдельным ответом на находку
независимого review: два повода из прежних семи в три категории не ложатся —
«новый риск безопасности, лицензии, приватности или расходов» и
«труднообратимое изменение». Оба **переходят к координатору**, и переходят под
условием, названным вместе с самим решением: **каждый такой случай координатор
пишет строкой в журнал gate-решений**. Условие не косметическое — оно и есть
то, чем переданное полномочие отличается от тихо исчезнувшей эскалации: решение,
принятое координатором и нигде не записанное, неотличимо от непринятого
(преамбула журнала).

**Куда делись остальные пять поводов — сказано, а не подразумевается.** Выход за
пределы одобренного, изменение продуктового обещания и scope — геймплейные и
продуктовые решения; конфликт с принятым ADR и ADR с непринятым решением —
архитектурные; **нехватка полномочий** — блокер по построению, потому что
действие, права на которое владелец не давал, без него и не выполняется; «новое
решение» распадается по тем же трём категориям, а его процессную часть держит
мораторий (правило 11). Ни один из пяти не выпал — выпали ровно два названных
выше, и оба названы переданными, а не отменёнными.

**Ослабление ADR 0014 названо прямо.**
[ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §7 перечисляет
основания, которые эскалируются «по-прежнему», и два из них — новый риск
безопасности/лицензии/приватности/расходов и труднообратимое решение —
настоящее правило забирает координатору. **При расхождении буквы ADR с этим
разделом действует раздел.** §4 (независимый review каждого PR) не тронут и
сохраняется целиком; gameplay gate из того же §7 тоже остаётся за владельцем.

**Процедурный триггер поверх трёх категорий: отказ review в квалификации.**
**Решение владельца 2026-08-02.** PR, которому независимый review отказал в
квалификации под правило 7, идёт владельцу и требует команды `MERGE #N` —
**независимо от того, о чём был отказ**. Это не четвёртая категория и не
расширение списка: категории называют **предмет** решения, триггер срабатывает
по **факту** отказа. Читать их надо вместе — содержательный список один и в нём
три пункта, процедурный триггер один, — и смысл триггера в том, что отказ review
остаётся единственным внешним рычагом, оставшимся у проверяющей стороны после
того, как разрешение владельца на merge перестало запрашиваться по умолчанию.

**Правило 18 снято этим решением**, и снято предусмотренным им самим способом:
«сузить или снять его может только владелец отдельным решением». Секция правила
18 оставлена на месте с пометкой о снятии, а не удалена. Повод — разбор
нарушения: координатор смержил PR #178 по правилу 7, не дождавшись зелёного CI
(прогон был `pending`, постфактум зелёный на всех коммитах), назвал нарушение
сам и вынес владельцу два вопроса; владелец ответил расширением полномочий, а не
сужением.

**Что решение не отменяет** — названо явно, потому что иначе его прочтут шире,
чем оно есть:

- независимый review обязателен для **каждого** PR
  ([ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §4, правило 3);
- исход находки предлагает review, а не координатор; понизить находку до реестра
  против предложения review координатор не может (правило 4);
- квалификацию PR под правило 7 подтверждает независимый review, а не
  координатор единолично (правило 7), **и отказ review сохраняет прежнее
  последствие**: такой PR идёт владельцу за командой `MERGE #N` — пункт
  остаётся гарантией, а не названием;
- потолок кругов review — один разбор плюс один подтверждающий (правило 12);
- **gate-решение по gameplay-слайсу принимает владелец, играя**; merge его не
  заменяет.

Условия правила 7 (зелёный CI, `verify.ps1`, независимый review, Issue с
наблюдаемыми критериями) тоже не тронуты: расширение полномочий отвечает на
вопрос, чьего разрешения не нужно спрашивать, а не на вопрос, что проверяется
перед merge.

**Цена названа.** Единственной внешней проверкой перед merge остаётся
независимый review, и его вердикт становится более несущим, а не менее. Риск и
труднообратимость держатся теперь на дисциплине координатора писать строку в
журнал, а не на чужом «да». **Условие отката:** merge, сделанный по этому
правилу, пришлось откатывать из `main` → правило пересматривается, запись в
журнал.

## Исполнитель общается через репозиторий (2026-08-02)

**25. Исполнитель общается через репозиторий, а не через владельца.** **Решение
владельца 2026-08-02**, той же формой отмены моратория (правило 11), которую он
для себя предусматривает. Каналов три, и других нет:

- **работа** — в свою ветку;
- **результат и отчёт** — **в тело PR, который исполнитель создаёт сам**.
  Отдельного handoff нет: тело PR им и является;
- **остановка, вопрос, находка про чужую задачу** — комментарием в свою Issue.

**Повод измерен, а не предположен.** Внешние инструменты — Codex, opencode,
локальная модель — не находятся в сессии координатора, поэтому их отчёт
возвращался владельцу, и владелец **вставлял его руками**: при разнородном флоте
агентов он сам оказался транспортом между исполнителем и координатором. Слова
владельца: «вроде логично что исполнитель запишет все в ветку и создаст мр с
описанием а ты посмотришь».

**Почему прежний запрет был неверен.** «Публикация наружу сначала показывается
черновиком» — остаток правила, писавшегося, когда публиковал только координатор.
К собственному PR в собственном репозитории оно не относится: рискованный шаг —
**merge**, а не открытие PR. Побочно координатор перестаёт **переписывать** чужие
числа руками; на этом он в блоке #171/#77/#165 ошибся дважды, и один раз оболочка
съела обратные кавычки в уже опубликованном комментарии.

**Что правило не меняет** — названо явно, потому что иначе его прочтут шире, чем
оно есть:

- независимый review обязателен для **каждого** PR
  ([ADR 0014](../decisions/0014-parallel-agents-and-autonomy.md) §4, правило 3);
- **merge остаётся у координатора** и только при зелёном CI, зелёном review и
  Issue с наблюдаемыми критериями готовности (правило 7);
- отказ review в квалификации под правило 7 отправляет PR владельцу за командой
  `MERGE #N` (правило 24);
- координатор вправе править описание PR, и правку видит review;
- **черновик перед публикацией сохраняется там, где публикация действительно
  наружу** — чужие репозитории и внешние системы.

**Правило 8 применяется к телу PR — это то же правило, названное в новом месте, а
не новое обязательство.** Требование «число идёт с командой, которой снято, либо
со ссылкой на единственное место записи» всеобще и всегда таким было; до сих пор
оно соблюдалось само собой, потому что тело PR писал координатор. Теперь между
исполнителем и деревом нет второго читателя: координатор больше не пересобирает
handoff в описание и не снимает несостыковки по дороге, **первым читателем
описания становится review**. Пока у каждого числа названа команда, review
перепроверяет выборочно и дёшево (правило 15); как только появится число без
команды, отличить измерение от пересказа он сможет только перемерив всё сам — а
это цена другого порядка. Счёт блока #171/#77/#165: к классу «описание расходится
с деревом» относятся минимум четыре находки — пять мест guard'а вместо шести
(PR #180, `rg` даёт 6), числа соседнего правила в записи мутанта (PR #176),
диапазон 3,22–3,54, опускающий строку собственной таблицы (PR #185), «матрица» из
шести партий против пятнадцати прогонов (PR #178). **Ни одна не нашлась чтением
описания — все нашлись прогоном команды из него.**

**Цена названа.** Описание PR пишет тот, чью работу оно описывает, поэтому
приукрасить его стало легче. Защита прежняя и единственная — независимый review,
перегоняющий числа своими прогонами; именно он приукрашивание в блоке
#171/#77/#165 и ловил. **Условие отката:** независимый review пропустил
приукрашенное описание → правило пересматривается, запись в журнал.

## Вердикт review становится фактом в PR (2026-08-02)

**26. Вердикт независимого review публикуется комментарием в PR перед merge, и
публикует его координатор.** **Решение владельца 2026-08-02.** Формулировка
именно такая, потому что **reviewer read-only**: его бриф запрещает ему
публиковать комментарии, за весь блок #171/#77/#165 он не опубликовал ни одного,
и вердикты уходили handoff'ом, а в PR их переносил координатор. Формулировка «его
вердикт публикуется» это скрыла бы.

**Дыра, которую правило закрывает.** Вердикты блока жили **только в контексте
координатора**: при потере сессии доказательства того, что PR вообще проходил
review, не существовало бы. После снятия правила 18 и принятия правила 24
независимый review остался единственной внешней проверкой перед merge, поэтому
его результат обязан быть проверяемым фактом, а не практикой без источника.

**Отвергнутые варианты названы с ценой.** Файл `review/<PR>.md` в самой ветке —
наружу ничего не публикуется, но вердикт мержится вместе с кодом, который
одобрял. «Ничего не менять» — дешевле всего, но при автономном merge координатора
единственная внешняя проверка остаётся невидимой.

**Введено по ходу блока, а не с его начала**, и записывается в том объёме, в каком
подтверждается: комментарии есть у PR #180, #181 и #185, у PR #175 и #178 их нет
(`gh pr view <N> --json comments`).

**Цена названа.** Перенос делает координатор руками, и на этом он в блоке уже
ошибся: оболочка выполнила обратные кавычки в теле комментария как команды и съела
фразу из опубликованного вердикта PR #180. **Условие отката:** перенос продолжает
искажать вердикт → публикацию берёт на себя reviewer, и его read-only мандат
сужается явным решением, а не по ходу.

## Облегчение review и снятие потолка (решения владельца 2026-08-02)

Два правила и поправка к правилу 19 приняты во **второй** координационной сессии
2026-08-02 — темы «как облегчить review» и «перестроиться на разнородный флот».
Форма отмены моратория (правило 11) прежняя: явное решение владельца.
Формулировки подтверждены владельцем до записи. Поправка к правилу 19 записана
по месту, в самом правиле 19.

**27. Review облегчается тремя способами, и все три названы.**

1. **Дефолт reviewer — дешёвая модель.** Сильная модель остаётся по **маркерам
   риска правила 3** — детерминизм, канонический снапшот, design-контракт,
   словарь команд, продуктовое обещание, расширение полномочий агента. Маркеры
   здесь не переписываются: они уже написаны в правиле 3, и копия разошлась бы с
   источником (правило 8). **«Дешёвая» — средняя модель (Sonnet 5) по правилу 34
   (2026-08-07): младшего класса в проекте нет.** Это меняет маршрутизацию правила 14 ровно в одной
   точке: первый разбор review больше не получает сильную модель по умолчанию,
   он получает её по маркерам риска. Остальное правило 14 не тронуто — балансный
   слайс по-прежнему идёт сильной моделью, круги доработки и подтверждения —
   дешёвой, а дефолтный `reasoning_budget` остаётся `high` и действует в
   остатке.
2. **Условие отката — часть правила, а не пожелание.** Если за блок понижённый
   reviewer пропустит находку, которую поймает следующий круг review или playtest
   владельца, дефолт возвращается к сильной модели, и это записывается строкой в
   журнал gate-решений. Правило без записанного отката неотличимо от его
   отсутствия.
3. **Круг доработки отдаёт таблицу «находка → правка → команда, доказывающая
   правку»**, а подтверждающий круг проверяет только её.

Основание пункта 3 — измерение, а не мнение: круг доработки оставил остаток
**четыре раза подряд** (PR #175, #178, #176, #181 — счёт раздела `NOW`), и
структурную причину назвал сам независимый review: у круга доработки нет
собственной проверки полноты, его целиком читает только следующий круг. Там же
измерено, что три из четырёх послаблений потолка кругов пришлись на PR, где
предметом был **текст**, а не поведение.

**Отклонено, и записывается как отклонённое** — иначе вопрос вернётся:
**«ревьюер сам правит находки»**. Правила 4 и 7 стоят на одной конструкции:
сторона, чей merge разблокируется, не выдаёт себе ответ сама. Правящий reviewer
становится автором части PR, и независимого взгляда на эту часть не остаётся ни
у кого. Прецедент свой: на паке существ v2 вариант «координатор чинит сам и
мержит без третьего круга» был назван и отклонён этой же формулировкой (журнал,
2026-08-01).

**Отложено, не отменено:** spike по внешней дешёвой модели под review. Причина —
блочный reviewer (правило 19) введён 2026-08-02 и прожил один блок; менять класс
модели поверх неизмеренного рычага значит потерять оба измерения. Вернуться
после того, как снято число экономии от правила 19. Смена генеративного
инструмента дополнительно проходит процедуру
[`TECH_RADAR.md`](TECH_RADAR.md).

**28. Потолок записывающих агентов снят.** **Решение владельца 2026-08-02.**
Названная им причина: потолок ставился из-за токенов и производительности, а
флот перестроен — появились безлимитный локальный агент и дешёвый имплементор.

**Разделение труда, названное владельцем:** основная сессия ведёт merge, gate,
координацию и задачи классов `tier:deep` и `tier:critical`; реализация по
готовым критериям уходит на внешние дорожки `tier:fast` и `tier:standard`;
`tier:art` — Codex, как и было.

**Единственным ограничителем параллельной работы становится партиция по
файлам.** Она потолком не отменяется и никогда им не задавалась: две
записывающие задачи не владеют одним файлом — это правило про конфликты в
дереве, а не про бюджет. Четыре условия
[ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §3 для
именованного региона сохраняются без послаблений.

**Что снятием потолка НЕ отменяется** — записывается прямо, потому что иначе
прочтётся как «теперь всё параллельно»:

- **правило 1** — в блоке обязателен gameplay-слайс;
- **правило 2** — не более двух gameplay-слайсов, и считаются вопросы playtest,
  а не слайсы; **балансные слайсы не параллелятся никогда**. Это ограничение
  **не бюджетное**: playtest есть измерительный прибор, и два изменения
  симуляции, отвечающие на один вопрос, делают ответ владельца
  неинтерпретируемым;
- **правило 3** — независимый review каждого PR, без исключений по классу;
- worktree-изоляция, seed, checksum, replay, оценки токенов, checkpoints.

**Ослабление ADR названо в тексте правила** — как требует урок
[#183](https://github.com/anshushunov/dungeon-fortress/issues/183): правило 28
ослабляет [ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §5,
предписывавший возврат к потолку два при дефиците бюджета; условие возврата было
исполнено 2026-08-02 и затем отменено этим решением. **При расхождении буквы
ADR 0017 и правила 28 действует правило 28.**

**Условие отката:** появление в `main` revert, вызванного конфликтом
параллельных задач, либо второй случай нарушенной партиции за блок — потолок
возвращается, и это пишется строкой в журнал. **Место записи первого случая
названо здесь, иначе вторая половина условия не считается:** каждое нарушение
партиции координатор пишет строкой в журнал gate-решений — как счётчик `ADJUST`,
и по той же причине. Первый случай сам по себе отката не даёт, но без его записи
считать нечего, а правило без записанного отката неотличимо от его отсутствия
(пункт 2 правила 27 выше и критерий отказа ниже говорят это же).

**29. Три фичи могут писать в один файл одновременно, и порядок merge держит
координатор.** **Решение владельца 2026-08-03**, названная им причина: «мы очень
медленно движемся, берём тикет на геймплей и рядом море сапорт-тикетов».

Правило 28 оставляло единственным ограничителем партицию по файлам, и на
`Main.cs` — 5,6 тысячи строк, куда пишет почти всякая работа представления —
она стала главным тормозом. Теперь: **несколько записывающих задач берут один
файл**, если каждой назначены именованные методы, порядок merge назван **до
выдачи**, а rebase делает координатор. **Правило ослабляет
[ADR 0017](../decisions/0017-raise-parallel-writing-ceiling.md) §3**: тот
ограничивал регион двумя задачами, это правило снимает ограничение числа. Четыре
условия ADR 0017 §3 остаются, но перечисление членов ведётся по методам, а не по
всему файлу.

**Что этим НЕ снимается:** правило 2 (не более двух gameplay-слайсов, балансные
не параллелятся) — оно про измерительный прибор playtest, а не про конфликты в
дереве.

**Названный риск, ради которого правило записано, а не принято молча:** git
сливает непересекающиеся методы сам, а вот **порядок проходов отрисовки** —
нет. Две задачи, зелёные по отдельности, вместе дают кашу; так ловилась «метка
поверх существа» в [#83](https://github.com/anshushunov/dungeon-fortress/issues/83).
Ловит это не merge, а то, что кто-то держит целое, — то есть координатор, и это
его работа при каждом слиянии.

**Условие отката:** два сорванных merge за блок либо revert в `main` из-за
семантического конфликта — правило возвращается к файловой партиции, и это
пишется строкой в журнал.

**30. Блок берёт из долга только блокеры.** **Решение владельца 2026-08-03.**
Остальной долг живёт в очереди и в реестре, не занимая места в блоке: `ready`
висит постоянно, и его берёт любая свободная дорожка, когда захочет.

Измеренный повод: за 2026-08-03 смержено 12 PR, из них фич — четыре; остальное
долг и процесс. Правило 1 не отменяется — gameplay-слайс в блоке обязателен, —
меняется то, чем блок **добирается** до полного: фичами, а не долгом.

**Названная цена:** долг копится, и когда-нибудь его придётся разгребать целым
блоком. Владелец это принял.

**31. Числа тела PR прогоняются инструментом до review, а не глазами review.**
**Решение владельца 2026-08-03.** `scripts/check-pr-claimed-output.ps1` (PR #216)
гоняет исполнитель по собственному телу PR перед тем, как звать проверяющего.

Измеренный повод — тот же день: **три возврата из четырёх** были не про код, а
про утверждения (кадр показывал не то, что обещал; числа в контракте оказались
из другой метрики; правка чужого теста маскировала дефект). Код ни один reviewer
сломать не смог, включая мутанты, которых не было в брифах. Класс механический —
значит его место в прогоне, а не в самом дорогом агенте.

**Потолок кругов не трогается:** правило 12 остаётся, подтверждающий круг
остаётся. Сегодня именно подтверждающие круги нашли два настоящих дефекта.

**32. Мутант «убрать вызов» и мутант «перевернуть знак» — разные мутанты, и
первый не подразумевает второго.** **Решение владельца 2026-08-04.** Уточняет
правило 21, не заменяя его: мутант назначается **на каждое утверждение, которое
проверка делает**, а не на каждую половину изменения. Наличие и полярность — два
разных утверждения об одной строке.

**Измеренная цена — блокирующая находка на PR #235.** Гард требовал, чтобы вызов
поворота присутствовал в коде, и был доволен тем, что тело поворачивается **не в
ту сторону**. Два мутанта независимого review — «тело отворачивается от того,
кого бьёт» и «вся партия смотрит задом наперёд» — дали **592 пройдено, 0 не
пройдено**. Оба мутанта, назначенные брифом задачи, были одного рода, поэтому
полярность осталась непокрытой не потому, что её не проверили, а потому, что её
не отличили от наличия. Подтверждающий круг показал, что дыра шире одной строки:
**пять** его подстановок — отрицание внутри выражения, отрицание обёрткой вокруг
вызова, переименование связок при нетронутом литерале — тоже проходят; остаток
вынесен в [#237](https://github.com/anshushunov/dungeon-fortress/issues/237).

**Практическое следствие для брифа:** перечисляя мутанты, называй, **какое
утверждение** каждый из них опровергает. Если два мутанта опровергают одно и то
же утверждение, второй не нужен; если у утверждения нет мутанта — оно не
проверено, как бы ни выглядело покрытие.

**Что этим не отменяется:** правило 21 в части «для представления и документации
мутант назначается брифом» и правило 12. Число мутантов не растёт механически —
растёт число **названных утверждений**, а мутанты идут за ними.

**Условие отката:** если за блок ни один мутант второго рода не поймал ничего, а
брифы подорожали, — правило возвращается к прежней редакции, и это пишется
строкой в журнал.

**33. Состояние задачи в документе проверяется перечислением всех вхождений её
номера, а не прогоном по метке статуса.** **Решение владельца 2026-08-04.**
Уточняет правило 8 в части **способа проверки**, а не его требования.

**Измеренная цена — два возврата этой формы за один день, оба координаторские:**
второй круг PR #230 и PR #239. Форма одна: ячейка статуса правится, соседний
текст той же строки остаётся из прежней редакции, и документ начинает утверждать
про одну задачу две несовместимые вещи одновременно — «✅ сделано» в одном месте
и «`ready`, свободна» в другом.

**Счёт назван точно, потому что первая редакция этого правила назвала его
неточно.** Возвратов за день было три, но третий — первый круг PR #230 — содержал
находки **другого** рода: нетронутую диффом строку, арифметику возраста записей
реестра и склейку трёх эпизодов прецедента в один. Правило 33 их не ловит и не
претендует. Неточность нашёл независимый review PR #241 и назвал её «ровно тем
типом небрежной атрибуции истории репозитория, против которого правила 32 и 33 и
написаны»; исправлено до merge. Двух случаев достаточно для правила — трёх не
было. Команда, записанная координатором в
собственный критерий готовности (`rg -n "^\| \*\*Идёт"`), поймать это **не могла
по построению**: она ищет метку статуса, а ложь жила в описании рядом.
Независимый review находил дефект все три раза одним и тем же способом —
перечислял вхождения номера задачи и читал каждое.

**Практическое следствие:** правка, меняющая состояние задачи, проверяется
`rg -n "#<номер>" <файл>` с чтением **каждой** вернувшейся строки. Критерий
готовности, написанный как прогон по метке статуса, этому требованию не
удовлетворяет.

**Что этим не отменяется:** правило 8 целиком — оно про то, что состояние не
переносится копированием; правило 33 добавляет, **чем** это проверяется.

**Условие отката:** если перечисление начнёт возвращать столько строк, что
чтение каждой перестанет быть выполнимым, — правило заменяется на инструмент, и
замена пишется строкой в журнал.

## Класс модели по классу задачи (2026-08-07)

**34. Класс модели определяется меткой `tier:*` задачи, а не выбором
исполнителя.** **Решение владельца 2026-08-07** — единственное основание:
базовая линия [`TOKEN_BUDGET.md`](TOKEN_BUDGET.md) нашла 90,5 % вызовов на
`claude-opus-5` за 2026-07-26…2026-08-05, включая механическую работу (Issue
[#283](https://github.com/anshushunov/dungeon-fortress/issues/283)).

| Класс задачи | Класс модели |
|---|---|
| `tier:fast` | средняя (Sonnet 5) |
| `tier:standard` | средняя (Sonnet 5) |
| `tier:deep`, `tier:critical` | старшая (Opus 5) |
| независимый review | не ниже класса исполнителя |

Младшая модель (Haiku) не используется — отклонена владельцем как
недостаточная; младшего класса в таблице нет и не будет. Класс называется в
брифе обязательно — контракт агента [`AGENT_ENTRY.md`](AGENT_ENTRY.md).

**Эскалация.** Исполнитель поднимает класс сам, если задача оказалась сложнее
назначенного, и называет признак в теле PR (правило 25). Понижение класса
исполнителем не предусмотрено — это решение координатора в брифе, не находка
исполнителя.

**Согласование с правилами 14 и 27.** Оба говорят «дешёвая модель», не называя
класс явно; этим правилом «дешёвая» = средняя (Sonnet 5) — младшего класса
больше нет, читать дословно как раньше нельзя. Уточнение внесено в текст обоих
правил по месту.

**Проверка исполнения.** Доля вызовов `claude-opus-5` за срез — команда
«Распределение вызовов по моделям» [`TOKEN_BUDGET.md`](TOKEN_BUDGET.md);
методика там же, не переписывается. Точка отсчёта до внедрения правила снята
тем же способом — `evidence/283-model-share.json`. Критерий Issue #283 — доля
старшей модели за две недели после внедрения ниже 70 %.

**Условие отката:** PR вернулся с review по причине «сделано слишком слабой
моделью» → привязка класса пересматривается, запись в журнал.

## Потолок длины прогона

**35. Прогон записывающего агента заканчивается коммитом и передаточным
резюме до авто-компакции, а не после неё.** Решение владельца 2026-08-07 —
основание [`TOKEN_BUDGET.md`](TOKEN_BUDGET.md): один субагент дал 451 M cache
read за 778 вызовов, 9 % расхода субагентов проекта на одну задачу при медиане
18 M по 127 субагентам.

Правило строится на двух наблюдаемых признаках. Плановый потолок брифа —
**250 вызовов**.

**1. Авто-компакция или предупреждение о заполнении контекста — сигнал

бесплатна: продолжатель заново поднимает контекст, теряет то, что предшественник
знал и не записал, и стоит координатору отдельного брифа, поэтому «делим на k»
завышает выигрыш.

**Пересмотр величины потолка** после первого замера скриптом

**Передаточное резюме** — не отдельный файл, а сообщение коммита рубежа: что
сделано, что осталось, какие файлы трогать дальше, какие проверки уже
зелёные, коммит остановки. Продолжатель начинает с `git log` ветки, как и на
рубежах правила 10, а не с расследования.
