# Технологический радар

Статус: действует  
Последняя ручная проверка: 2026-07-26  
Регулярность: раз в две недели и перед новым вертикальным срезом

## Цель

Быстро замечать полезные новые возможности, не превращая проект в непрерывную
миграцию между свежими версиями.

Основной принцип: **быстро обнаруживать, проверять маленьким spike, обновлять
осознанно**.

## Что отслеживать

- стабильные релизы выбранного движка, особенно 2D, C#/.NET, headless, импорт,
  навигацию, UI и профилирование;
- .NET, C# и тестовые инструменты;
- MCP-адаптеры для движков и редакторов;
- способы наблюдения и управления игровым рантаймом агентами;
- инструменты CI, статического анализа, тестирования и профилирования;
- официальные модели и API генерации изображений;
- инструменты согласованности стиля, спрайтов, анимации, звука и локальных
  генеративных моделей;
- изменения лицензий, цен, условий использования, безопасности и приватности.

## Источники

Использовать в первую очередь:

1. официальные release notes, документацию и security advisories;
2. GitHub Releases, changelog и issues самого инструмента;
3. воспроизводимый локальный эксперимент;
4. вторичные обзоры только как источник кандидатов для проверки.

Версии, даты, цены и возможности нельзя переносить в решение по памяти без
актуальной ссылки.

## Оценка кандидата

Для каждого материального изменения записать:

- что изменилось по сравнению с используемой версией;
- какой конкретный игровой или агентский сценарий улучшится;
- зрелость: stable, preview, experimental или abandoned;
- совместимость с проектом и другими инструментами;
- стоимость миграции, новые зависимости и способ отката;
- влияние на детерминизм, производительность и безопасность;
- минимальный эксперимент, способный подтвердить пользу.

После оценки присвоить действие:

- **Ignore** — проекту сейчас не полезно.
- **Assess** — наблюдать и собрать больше данных.
- **Trial** — проверить изолированным spike.
- **Adopt** — предложить обновление через Issue/ADR/PR.
- **Hold** — не использовать из-за известного риска или несовместимости.

## Правила обновления

- Во время вертикального среза версии заморожены, кроме исправлений безопасности,
  потери данных или блокирующих дефектов.
- Обычные обновления выполняются между срезами.
- Движок, SDK, MCP-плагины и генеративные модели закрепляются точной версией или
  идентификатором модели, когда инструмент это позволяет.
- Обновление сначала проходит на отдельной ветке и воспроизводимом сценарии.
- Существенное изменение архитектуры, лицензии или пайплайна требует ADR.
- Автоматический мониторинг ничего не устанавливает и не изменяет сам.

## Автоматизация

В Codex настроена задача `Dungeon Fortress — tech radar`, запускающаяся раз в две
недели по понедельникам. Она:

- читает актуальные ADR и сравнение стека;
- проверяет первичные источники;
- сообщает только о значимых изменениях со ссылками;
- предлагает `Ignore`, `Trial`, новый ADR или обновление;
- не устанавливает зависимости, не меняет код и не создаёт PR автоматически.

Если автоматизация недоступна, эту же процедуру выполняет агент перед новым
вертикальным срезом.

## Инструкция по установке окружения

Пока ADR 0003 имеет статус `Proposed`, установка движка не считается частью
канонического окружения. После успешного технического spike и принятия стека
агент обязан создать `docs/engineering/ENVIRONMENT_SETUP.md` с:

- точными версиями и официальными ссылками;
- обязательными и необязательными компонентами;
- командами проверки установки;
- настройкой MCP и локального Agent Bridge;
- инструкцией полного удаления или отката;
- минимальным smoke-тестом готовности окружения.
