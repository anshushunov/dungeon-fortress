# Roadmap разработки

Статус: живой план  
Дата обновления: 2026-07-28  
Владелец направления: владелец проекта  
Источник конкретной работы: GitHub Issues и Pull Requests

## Зачем нужен этот документ

Roadmap показывает не все возможные механики, а **какую игровую гипотезу мы
проверяем сейчас, что уже доказано и где владелец выбирает дальнейшее
направление**.

У roadmap нет календарных обещаний. Проект разрабатывается одним человеком с
агентами и движется короткими запускаемыми срезами. Поэтому следующий крупный
этап уточняется после человеческого playtest, а не планируется заранее до
деталей.

Стабильное продуктовое обещание находится в [`VISION.md`](VISION.md), главная
идея и core gameplay — в [`PITCH.md`](PITCH.md), текущее устройство механик — в
`docs/design/`, причины важных решений — в `docs/decisions/`. Этот документ
отвечает только на вопросы «где мы сейчас?» и «какие направления можно выбрать
дальше?».

## Как владелец управляет направлением

После каждого playtest владелец даёт одну из команд:

| Команда | Что происходит |
|---|---|
| `CONTINUE` | Начинается следующий минимальный шаг текущего эксперимента. |
| `ADJUST: <что изменить>` | Следующий шаг не начинается; текущий slice исправляется и проверяется снова. |
| `PROMOTE: <направление>` | Указанное направление становится следующим активным прототипом. |
| `DEFER: <направление>` | Направление остаётся в roadmap, но не получает Issue. |
| `STOP` | Эксперимент закрывается без дальнейшего расширения. |
| `MERGE #N` | Владелец явно разрешает merge уже проверенного PR. |

Координационный чат фиксирует решение в PR или Issue, обновляет раздел `NOW`
этого документа на границе прототипа и только затем создаёт следующий
implementation Issue.

## Правила движения

- Одновременно активен один gameplay slice и не более одной небольшой
  обеспечивающей задачи по tooling или art.
- Каждый шаг заканчивается запускаемой игрой, зелёными проверками и playtest
  владельца.
- Следующий gameplay Issue не реализуется до решения
  `CONTINUE / ADJUST / PROMOTE / DEFER / STOP`.
- Claude Code является основным пишущим агентом. Координационный чат ведёт
  roadmap, декомпозицию, продуктовые развилки, приёмку и генерацию ассетов.
- Сгенерированные ассеты сначала получают prompt и provenance, затем передаются
  implementation-агенту для подключения.
- Roadmap обновляется на decision gate, а не после каждого технического коммита.
- Новые движки, SDK, MCP и генеративные инструменты проверяются по
  `docs/engineering/TECH_RADAR.md` на границе прототипов либо перед крупным
  обновлением, но не ради каждой новой версии.

### Чего мы не делаем

Эти формулировки дешевле принять заранее, чем спорить о них на decision gate.

- **Не строим симуляцию ради симуляции.** Система без наблюдаемого игроком
  последствия не входит в срез.
- **У каждой новой системы есть бюджет читаемости в UI.** Если её нельзя
  показать игроку, её не добавляем.
- **Не универсализируем заранее.** Один объект и одно последствие вместо
  каталога и редактора.
- **Pre-production не длится бесконечно.** См. критерий отказа ниже.

### Критерий отказа

> Два `ADJUST` подряд по одной гипотезе без улучшения на playtest закрывают
> возможность третьего. Владелец выбирает `PROMOTE` или `STOP`.

Без этого правила `ADJUST` может крутиться бесконечно, а `STOP` останется
словом в словаре, которое никогда не будет применено.

## Целевая игра

Продуктовый фокус и ответ на вопрос «что здесь самое интересное» находятся в
[`PITCH.md`](PITCH.md) — документ принят владельцем 2026-07-28. Roadmap ему не
противоречит и не дублирует его: порядок кандидатов ниже следует разделу 11
питча.

Обещание в одном абзаце:

> Игрок вырубает из скалы собственное подземное владение и населяет его
> существами, которые живут своей жизнью. Он не отдаёт приказов — он проектирует
> пространство, задаёт правила и иногда вмешивается рукой. Владение растёт,
> начинает притягивать новых обитателей, обзаводится производством, обороной и
> внутренними конфликтами. Регулярно приходят те, кто хочет забрать накопленное.
> Каждая партия оставляет несколько историй, которые игрок может пересказать
> словами.

Критерий приоритизации, вытекающий из питча: **работа, усиливающая столкновение
плана и людей, важнее работы, усиливающей подготовку или проверку.**

Игры, за которыми стоит идти за конкретными решениями, и то, за чем именно к
каждой из них идти, перечислены в [`REFERENCES.md`](REFERENCES.md).

### Milestones

Это не календарный план и не порядок работ. Это направление, по которому на
каждом gate можно сравнивать кандидатов между собой.

| Milestone | Содержание | Критерий выхода |
|---|---|---|
| **A — Vertical Slice** | Одна сессия ~30 минут. Копание и функциональные комнаты; 2–3 связанные производственные цепочки; несколько волн нарастающей угрозы; явный счёт владения; нарративная лента; рука хозяина; свет, автотайлинг, интерполяция, звук. | Владелец играет три партии подряд по собственному желанию и может пересказать историю из каждой. |
| **B — Playable Loop** | Сессия 1–2 часа. Приток населения от условий владения; комнаты со свойствами; экипировка и мастерская; двери и ловушки; черты характера и лёгкие отношения; травмы, мораль, восстановление; сохранение/загрузка; именованные враги-герои. | Партия играется без участия разработчика и заканчивается по решению игрока, а не по таймеру. |
| **C — Content Alpha** | Кампания. Несколько видов существ с разными потребностями; процедурная карта либо набор авторских; глобальный слой (один внешний ресурс, одна угроза, одно решение); art-direction gate и production-пайплайн; баланс и кривая сложности. | Посторонний играет 2 часа без объяснений. |

Постоянные ограничения на всех milestone: 2D и посильный объём контента для
одного человека с агентами; детерминизм, replay и headless-проверки не
приносятся в жертву ни одной фиче; каждая новая система имеет бюджет
читаемости в UI.

### NOW — завершить одну функциональную комнату

Активная продуктовая гипотеза:

> Если игрок сам освобождает пространство, организует логистику и превращает
> новую комнату в работающий объект, появляется ли ощущение хозяина живого
> подземелья, а не наблюдателя за тестовой симуляцией?

Минимальная цепочка:

```text
обозначить скалу
    → автономно выкопать
    → получить и складировать Stone
    → разместить blueprint тренировочного поста
    → доставить Stone на стройку
    → автономно построить
    → назначить TrainingGround
    → увидеть реальные Drill jobs
```

Ближайшие шаги. Обеспечивающие задачи идут последовательно, по одной за раз, и
предшествуют генерации ассетов: они не расходуют бюджет генерации и дают больше
видимого эффекта, чем art pass.

1. Enabling Issue
   [#28](https://github.com/anshushunov/dungeon-fortress/issues/28): сделать
   текст и переполнение graybox UI проверяемыми без golden PNG.
2. Presentation pass A (см. раздел «Представление»): интерполяция движения между
   тиками и переверстка HUD на Control-контейнеры.
3. Сгенерировать небольшой asset pack тренировочного поста
   (`blueprint / construction / completed`) в геометрии
   [ADR 0008](../decisions/0008-three-quarter-projection.md).
4. Реализовать functional-room slice отдельным Issue и Draft PR.
5. Провести owner playtest на 5–10 минут.

Критерии выхода:

- игрок понимает разницу между своим blueprint и автономным исполнением;
- Stone физически проходит от склада до стройки и не исчезает из учёта;
- построенный объект меняет симуляцию, а не только картинку;
- новую комнату можно получить из выкопанного пространства;
- причины ожидания, доставки, строительства и начала тренировки читаются без
  исходного кода или сырого лога;
- владелец хочет изменить планировку или приоритет и попробовать ещё один
  вариант.

Owner decision gate после functional room:

- `PROMOTE SESSION LOOP` — повторяющийся цикл угрозы и счёт владения; это
  ожидаемый следующий шаг по порядку доказательства питча;
- `CONTINUE CONSTRUCTION` — двери, стены, ловушки и свойства комнат;
- `PROMOTE NARRATIVE` — нарративная лента поверх существующего event log;
- `ADJUST` — исправить текущую цепочку до расширения;
- `STOP` — строительство не даёт нужного ощущения, выбрать другую гипотезу.

## Кандидаты после текущего gate

Это направления, а не уже утверждённая очередь. Implementation Issues для них
не создаются до выбора владельца.

Порядок соответствует разделу 11 [`PITCH.md`](PITCH.md): сначала то, что
усиливает столкновение плана и людей, потом то, что усиливает подготовку и
проверку. Номера срезов ниже — это номера из питча.

### Срез 1, рекомендуемый — повторяющийся цикл угрозы и счёт владения

Гипотеза:

> Если угроза приходит несколько раз за сессию с нарастающей силой, а между
> волнами владение восстанавливается и перестраивается, игрок связывает своё
> решение с последствием и начинает управлять осознанно, а не наблюдать.

Минимальный slice: 3–5 набегов вместо одного, фаза восстановления между ними,
явный счёт владения по итогам сессии.

Почему первым:

- решение проверяется несколько раз за партию — игрок видит связь причины и
  следствия. Единственный набег через ~25 минут после решения даёт ровно ту
  разрежённость обратной связи, которая уже привела к результату playtest
  *«Perceived influence: not confidently perceived»*;
- появляется ритм сессии: тишина → тревога → бой → разбор → перестройка;
- поражение перестаёт быть концом и становится сюжетом;
- закрывается наблюдение P2 из
  [`PROTOTYPE_01_EVALUATION.md`](../playtests/PROTOTYPE_01_EVALUATION.md), где
  гипотеза H2 помечена contradicted, потому что метрика потерь делает `overrun`
  «лучше». Это не дефект метрики, а отсутствие функции ценности: игра нигде не
  говорит, что такое «хорошо»;
- **любой** следующий кандидат получает нормальный испытательный стенд.

Стоимость низкая: таймер угрозы, генератор налётчиков, правила боя и исход уже
реализованы и покрыты тестами. Речь о параметризации существующего.

Требует закрытия двух открытых развилок питча — смерть обитателей и длина
партии (раздел 10 `PITCH.md`).

### Срез 2 — нарративная лента

Гипотеза:

> Если события владения рассказывать именами и предложениями, а не reason
> codes, владелец получает пересказываемую историю без введения памяти и
> отношений.

Минимальный slice: агрегатор поверх существующего event log, превращающий
записи в человеческие фразы и отмечающий редкие события как «моменты сессии».

Сырьё уже есть в каноническом состоянии: именованные существа со стабильными
`id`, `lastDecision` с reason code и аргументами, event log с дедупликацией,
индивидуальные боевые исходы. Не хватает слоя перевода, а не слоя симуляции.

Побочная польза: закрывает открытый вопрос «как показывать причину поведения,
не превращая экран в лог».

### Срез 3 — сопротивление плану

Гипотеза:

> Одна амбиция, один наблюдаемый отказ и одна видимая причина делают обитателя
> участником, а не исполнителем.

Это возврат к отложенному обещанию ADR 0002/0006 — с этого среза отсрочка
заканчивается. Первый slice остаётся маленьким: одна память или связь, одно
наблюдаемое влияние на решение, а не полноценная социальная модель.

Порядок важен: лента идёт раньше, иначе новая связь между существами останется
числом в снапшоте.

### Срез 4 — приспешники и указы

Один приспешник, один указ, одно искажение намерения характером. Граница
принята владельцем: назначить роль можно, приказать действие нельзя. Реализация
начинается только после ADR, уточняющего
[ADR 0005](../decisions/0005-indirect-command-contract.md).

### Срез 5 — пространство как оружие

Свет и тьма меняют исход волны: освещённое повышает эффективность работы,
неосвещённое обороняет. Работа по освещению нужна и для читаемости картинки —
здесь она получает игровой смысл вместо роли настройки рендера.

### Срез 6 — экономика вооружает защитников

Гипотеза:

> Производственная цепочка интереснее, если ограниченный ресурс можно потратить
> на развитие владения либо на снаряжение конкретных автономных защитников, а
> последствия видны в следующем набеге.

Возможный минимальный slice:

```text
сырьё → перевозка → мастерская → простое оружие
      → автономное получение снаряжения → изменённый бой/травма
```

Сильный кандидат, но стоит последним осознанно: снаряжение проверяется один раз
за сессию и без среза 1 не имеет стенда, на котором его влияние было бы видно.

### Вне порядка питча — глубина строительства

Минимальный вопрос: создают ли двери, стены, ловушки или свойства комнаты
интересный выбор пространства, а не только больше кнопок?

Это продолжение текущей линии, а не шаг питча, поэтому доступно по
`CONTINUE CONSTRUCTION` сразу после functional room. Начинать с одного объекта
и одного последствия для маршрута или боя.

## Представление

Это **не** production art. Проекция закрыта
[ADR 0008](../decisions/0008-three-quarter-projection.md); здесь перечислена
работа слоя отрисовки, которая уже дважды блокировала playtest и оценивается
по отношению «эффект / стоимость».

Причина, по которой это отдельный от art раздел: плавности сейчас нет по
архитектурной причине, а не по художественной. `TicksPerSecond = 6.0`, позиция
существа равна `tile * TileSize` — существо телепортируется на размер тайла
шесть раз в секунду. Никакой генеративный пайплайн этого не исправит.

| # | Работа | Что даёт | Состояние |
|---|---|---|---|
| 1 | Отделить рендер от тика, интерполировать позицию по `alpha` между тиками | Единственная причина отсутствия плавности | Presentation pass A |
| 2 | Переверстать HUD на Control-контейнеры вместо абсолютных `Rect2` | Закрывает коллизии текста навсегда: причина — фиксированный viewport и абсолютные позиции лейблов, а не мелкий шрифт | Presentation pass A, опирается на Issue #28 |
| 3 | `TileMapLayer` с terrain/autotile, тайл верх + фасад | Геометрия пещеры вместо контурных квадратов | Реализация ADR 0008 |
| 4 | Тайл 22 → 32–48 px, камера с зумом и панорамой, Y-sort | При 22 px спрайт физически не способен показать направление и состояние | Реализация ADR 0008 |
| 5 | `CanvasModulate` + `PointLight2D`, тьма вне освещённого | Сетка становится подземельем; больше эффекта, чем от любого art pass | Связано со срезом 5 — свет как механика |
| 6 | Процедурная анимация: facing и flip, bob при ходьбе, наклон, squash & stretch на ударе | ~80 % «живости» без единого нового кадра | Кандидат |
| 7 | Партиклы, hit-stop, вспышка, всплывающие числа урона | Делает бой читаемым — прямая жалоба из playtest | Кандидат |
| 8 | Иконки-мысли над головой (еда / устал / «!») | Читаемость намерений без открытия инспектора | Кандидат |

Пункты 1–2 выполняются **до** следующей генерации ассетов: они не расходуют
бюджет генерации и дают больше видимого эффекта, чем весь art pass.

## LATER — только после подтверждения локального ядра

### Глобальный уровень

Фракции, поселения, торговые маршруты, вылазки и события внешнего мира нужны
игре, но пока не должны определять архитектуру локального прототипа. Первый
global spike начинается только когда:

- локальная экономика содержит минимум две связанные цепочки;
- пространство влияет на производство или защиту;
- именованные существа имеют хотя бы один проверенный источник индивидуальной
  истории;
- автоматический конфликт имеет понятные входы и последствия.

Глобальный уровень сначала поставляет локальному владению один ресурс, одну
угрозу и одно решение. Полная симуляция мира не является первым шагом.

### Production art и масштаб контента

**Представление и production art — разные вещи с разными gate.** Работа слоя
отрисовки идёт сейчас (раздел «Представление»), потому что без неё playtest
измеряет качество рендера, а не качество механики. Откладывается сюда только
production art.

До подтверждения игрового ядра используются небольшие воспроизводимые asset
packs в геометрии [ADR 0008](../decisions/0008-three-quarter-projection.md).
Полный художественный pipeline, большой каталог существ, анимаций, биомов и
интерфейсов, выбор палитры и уровня стилизации откладываются до отдельного
art-direction gate.

Способы получения анимации, включая cutout-скелет и пререндер 3D, описаны в
[`ANIMATION_PIPELINE.md`](../art/ANIMATION_PIPELINE.md). Специализированные
генеративные инструменты выбираются spike-процедурой
`docs/engineering/TECH_RADAR.md`, а не из обсуждения.

## Постоянные workstreams

| Направление | Текущее состояние | Следующее доказательство |
|---|---|---|
| Construction | Активно: functional room | Выкопать, построить и использовать одну новую комнату. |
| Session loop | Один набег за сессию, функции ценности нет | Несколько волн подряд меняют решения игрока между ними. |
| Narrative | Event log и reason codes есть, слоя перевода нет | События владения читаются как история, а не как коды. |
| Economy | Пища и Stone logistics работают | Ввести альтернативную стоимость и связь со снаряжением/боем. |
| Combat/RPG | Автоматический raid, HP, injuries, morale | Показать влияние одного произведённого предмета или навыка. |
| Individuality/simulation | Имена, свойства и история решений есть; память/отношения отложены | Одна память или связь меняет следующее решение. |
| Global layer | Не начат | Один внешний источник ресурса/угрозы после подтверждения локального ядра. |
| Представление | Graybox, фиксированный кадр, без интерполяции | Интерполяция, Control-вёрстка HUD, автотайлинг и камера прошли playtest. |
| Art | Первый goblin pass, проекция закрыта ADR 0008 | Asset pack постройки и читаемая цепочка blueprint → complete. |
| Agent tooling | Deterministic CLI/API/MCP работают | Issue #28; затем radar check перед следующим прототипом. |

## Когда roadmap пересматривается

Обязательное обновление происходит:

1. после owner gate текущей функциональной комнаты;
2. после следующего выбранного вертикального прототипа;
3. перед первым global-layer spike;
4. при срабатывании критерия отказа — два `ADJUST` подряд без улучшения;
5. если новое технологическое ограничение меняет стоимость или проверяемость
   разработки агентами;
6. если меняется продуктовый фокус в [`PITCH.md`](PITCH.md) — порядок кандидатов
   следует за питчем, а не наоборот.

Если roadmap расходится с Accepted ADR или актуальным design-контрактом, он не
переопределяет их молча: сначала оформляется новое решение или обновляется
контракт, затем roadmap.
