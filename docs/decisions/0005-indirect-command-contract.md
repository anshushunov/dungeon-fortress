# ADR 0005: Команды игрока не адресуют конкретное существо

- Статус: Proposed
- Дата: 2026-07-26
- Ответственные: владелец проекта и агенты разработки

## Контекст

`docs/product/VISION.md` объявляет непрямое управление первым опорным принципом,
но до сих пор это было дизайнерским намерением, а не проверяемым ограничением.
Ничто в репозитории не мешает добавить команду вида «существо 4, иди работать».

Одновременно spike Issue #3 оставил работающий контракт команд
`SimulationCommandDocument` `schemaVersion: 1` с полями
`{tick, agentId, energyDelta}`. Он адресует конкретного агента по идентификатору.
Для нагрузочного и детерминистского spike это было правильно: команда там —
инструмент теста, а не игровой ввод.

Issue #8 фиксирует контракт первого вертикального прототипа, а Issues #9, #10 и
#11 строят на нём headless-ядро, интерактивный graybox и бой. Все три должны
принимать один и тот же ввод. Решение о форме этого ввода принимается один раз и
дальше становится дорогим: оно определяет схему команд, публичную поверхность
domain MCP, путь ввода в Godot и структуру всех сценарных fixtures.

## Рассмотренные варианты

### Оставить схему v1 и добавить игровые команды рядом

Дешевле всего: одна схема, один загрузчик. Но `agentId` остаётся в контракте, и
поле «кому» присутствует в каждой команде. Практика показывает, что доступное
поле рано или поздно используется: сначала для отладки, потом для UI «отправить
этого копать». Ограничение остаётся словесным и не проверяется тестом.

### Разрешить прямое управление как «отладочный» канал

Позволяет быстро воспроизвести любое состояние в тесте. Цена — прототип перестаёт
доказывать основную гипотезу: невозможно отличить «автономный выбор сработал» от
«его продавили командой». Также появляется соблазн выпустить отладочный канал в
graybox.

### Отдельная схема v2 без адресации существа

Схема команд прототипа не содержит `creatureId`, `jobId` и координаты цели атаки
вовсе. Отсутствие поля делает нарушение принципа невыразимым, а не запрещённым на
словах. Цена — вторая схема команд и явная граница между spike-харнессом и
игровым вводом.

## Решение

Принять третий вариант для Prototype 1. Применение того же ограничения после
оценки Prototype 1 потребует отдельного подтверждения или нового ADR:

- вводится `SimulationCommandDocument` `schemaVersion: 2` — игровой ввод
  прототипа; его словарь ограничен `zone_paint`, `zone_erase`, `set_priority`,
  `set_rule` и описан в
  [`docs/design/PROTOTYPE_01_PREPARE_FOR_RAID.md`](../design/PROTOTYPE_01_PREPARE_FOR_RAID.md);
- v2 имеет закрытую корневую схему `{schemaVersion, scenario, seed, commands}`;
  `scenario` является только диагностической меткой и не влияет на состояние,
  а неизвестные/смешанные поля v1 и v2 отвергаются;
- ни одна команда схемы v2 не содержит поля, идентифицирующего существо,
  конкретную работу или цель атаки; неизвестное поле отвергает всю команду;
- игрок влияет на распределение труда только через среду (зоны), важность
  (приоритеты) и законы владения (правила);
- схема v1 сохраняется исключительно как вход детерминистского spike-харнесса и
  не используется как игровой ввод; gameplay entry points не принимают v1,
  автоматического преобразования между версиями нет, расширять v1 не следует;
- Godot, CLI и domain MCP принимают один и тот же словарь v2 и валидируют его
  одинаково; путь ввода в UI не имеет привилегий относительно headless;
- команда применяется атомарно: либо целиком, либо отвергается до любой мутации;
- управление темпом (`pause`, `step`, скорости) не является командой, не попадает
  в журнал и не влияет на каноническое состояние.

## Последствия

Становится проще:

- доказать основную гипотезу прототипа — автономность нельзя подделать вводом;
- проверять реплей: один журнал команд воспроизводит сессию независимо от того,
  пришли команды из UI, CLI или MCP;
- писать негативные тесты: попытка адресовать существо не проходит валидацию по
  структуре, а не по прикладной проверке.

Становится сложнее:

- готовить произвольное состояние в тесте: чтобы существо оказалось голодным,
  сценарий обязан довести его до этого правилами, а не установить поле напрямую.
  Это осознанная цена; тестовые фабрики состояния остаются внутренним API
  симуляции и не являются командами игрока;
- поддерживать две схемы команд, пока spike-харнесс не выведен из употребления;
- вводить будущие механики, которым понадобится адресный ввод (назначение героя,
  ручной приказ в бою). Такая механика потребует нового ADR, заменяющего этот, а
  не «ещё одного поля».

Ограничение действует на срок жизни Prototype 1. Если оценка Issue #12 покажет,
что непрямое управление не даёт игроку ощущения влияния, замена решения
оформляется новым ADR со ссылкой на этот.

## Проверка решения

- в схеме v2 отсутствуют поля адресации существа, работы и цели атаки; тест
  проверяет отклонение документа с любым таким полем;
- `prepared` и `neglected` задаются только командами v2, а `baseline` не
  использует команд вовсе — то есть различие между сценариями целиком лежит в
  безадресном словаре;
- в `prepared` наблюдаемо меняется поведение владения без единой адресной
  команды, и различие подтверждается инвариантами раздела 13.4 контракта;
- graybox Issue #10 отправляет ровно те же команды, что headless; тест
  сравнивает каноническое состояние прогонов из UI-журнала и из файла;
- независимый reviewer подтверждает, что в diff нет обходного адресного канала.
