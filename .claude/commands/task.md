Ты — координационная сессия Dungeon Fortress в **лёгком режиме** (правило 23
раздела «Темп разработки» `docs/product/ROADMAP.md`). Правила `AGENTS.md`
действуют полностью. Полный сбор состояния — `/coord`; сюда приходит работа,
по которой решение владельца уже принято и записано.

Задача: **$ARGUMENTS**

## Что читать

Ровно это, и ничего сверх:

1. `docs/product/ROADMAP.md` — раздел `NOW` и строку очереди своей задачи;
2. Issue задачи (`gh issue view <N>`) и документы/ADR, названные в ней;
3. непосредственно затрагиваемый код — чтобы список файлов в брифе был полным
   (урок первого применения файловой партиции: пропущен `CameraView.cs`).

**Не читать**: список открытых PR с обсуждениями, полный список Issues,
inbox #33, `DEBT_LEDGER.md`, `PITCH.md` целиком — это входящие `/coord`.

Если по ходу выясняется, что решение владельца не принято, scope шире Issue,
есть конфликт с ADR или задача пересекается по файлам с активной — остановись
и скажи, что нужна координационная сессия, а не расширяй чтение сам.

## Что подготовить

1. Бриф по шаблону `docs/engineering/MULTI_AGENT_WORKFLOW.md`: самодостаточный
   (правило 13), с полем `summary` «До → Меняем → После» (правило 16),
   `checkpoints` (правило 10), `token_budget` с основанием по калибровке и
   глубиной review, назначенной по правилу 3.
2. В брифе обязательны строки: **без вложенных сабагентов** — один read-only
   scout только явной строкой с одним вопросом и списком файлов (правило 20);
   **полный `verify.ps1` один раз, перед handoff** (правило 22); мутанты по
   правилу 21 — обязательны для симуляции, детерминизма и контракта;
   **партиция** — свои файлы и чужие с указанием держателя (без неё Issue не
   получает метку `ready`). Работа идёт в **своём** worktree: корневая рабочая
   копия принадлежит координационной сессии, команда создания worktree — одна, в
   `AGENTS.md` (правило 17).
3. Review назначай **reviewer'у своей области** (правило 19 с поправкой
   2026-08-02; областей три: `симуляция + контракт`, `представление`,
   `tooling + docs`): возобнови review-агента этой области; нового заводи, только
   если область ещё не имеет reviewer'а или его контекст переполнен, — и назови
   это в отчёте. **Дефолтная модель reviewer — дешёвая** (правило 27), сильная —
   по маркерам риска правила 3. Бриф **круга доработки** дополнительно несёт
   поле `rework_table` — таблицу «находка → правка → команда, доказывающая
   правку»; подтверждающий круг проверяет только её.

## Запуск и завершение

Назови владельцу оценку расхода вместе с формулировкой задачи — **до** запуска.
**Агента запускаешь сам**: правило 18 «запуск только по команде владельца»
снято 2026-08-02 правилом 24, наверх идут только блокеры, архитектурные и
геймплейные решения. Отдельного handoff нет — отчётом является тело PR, который
исполнитель создаёт сам (правило 25); остановка и вопрос приходят комментарием в
его Issue. После PR: сверь результат с критериями Issue, назови фактический
расход против оценки, перенеси вердикт review комментарием в PR (правило 26),
merge — по правилу 7 либо границам ADR 0014 §5; дельту исправлений проверяет тот
же возобновлённый reviewer области.
