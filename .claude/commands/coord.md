Ты начинаешь **координационную сессию** по Dungeon Fortress.

Роль описана в `docs/engineering/MULTI_AGENT_WORKFLOW.md`: декомпозиция
направления в Issues, продуктовые развилки, приёмка результатов и ведение
roadmap. Правила `AGENTS.md` действуют полностью.

Тема этой сессии: **$ARGUMENTS**
Если тема не указана, определи её сам из входящих и состояния проекта.

## Шаг 1. Собрать состояние

Выполни параллельно, не пересказывая вывод пользователю:

- `git fetch --prune` и `git status --short --branch`;
- `gh pr list --state open`;
- **для каждого открытого PR** — `gh pr view <N> --comments` и
  `gh pr view <N> --json reviews`. Обсуждение PR не переживает merge: после
  него комментарии перестают попадаться на глаза, поэтому разбирать их нужно
  до merge, а не после;
- `gh issue list --state open --limit 30`;
- `gh issue view 33 --comments` — coordination inbox;
- прочитай `docs/product/PITCH.md` — продуктовый фокус и критерий
  приоритизации;
- прочитай `docs/product/ROADMAP.md`, раздел `NOW` (если файл ещё не в `main`,
  посмотри его в открытом PR);
- прочитай последний по номеру файл в `docs/decisions/` и `docs/README.md`
  раздел «Следующий номер».

Читай документы, а не восстанавливай контекст по памяти или прошлым сессиям:
чат и автоматическая память Claude не являются источником истины.

## Шаг 2. Разобрать входящие

Входящими считаются неразобранные комментарии в Issue #33 **и** неразобранные
предложения в обсуждениях открытых PR. Каждое из них отнеси ровно к одному
исходу:

| Исход | Что делаешь |
|---|---|
| Реализуемая работа | Предлагаешь Issue: scope, non-goals, deliverables, критерии готовности, способ проверки |
| Продуктовая развилка | Предлагаешь раздел в `docs/product/` или ADR со статусом `Proposed` |
| Уже решено | Даёшь ссылку на документ, ADR или PR |
| Преждевременно | Оставляешь во входящих и называешь decision gate, к которому вернуться |
| Не делаем | Формулируешь причину и, при значимости, строку в анти-scope |

Ничего не публикуй на этом шаге — сначала покажи разбор.

## Шаг 3. Отчёт владельцу

Выдай короткую сводку в этом порядке:

1. **Где мы** — активный slice и его состояние одной строкой.
2. **Ждёт владельца** — открытые PR и развилки, требующие решения, с указанием,
   какое именно решение нужно.
3. **Входящие** — разбор новых записей из #33.
4. **Предлагаю дальше** — один следующий шаг с обоснованием, а не список опций.

## Границы роли

- Merge задач классов `defect`, `support`, `blocks-verification` и `art`
  выполняется без владельца при зелёном CI, зелёном `verify.ps1` и зелёном
  независимом review, если не затронуты контракт, словарь команд, ADR и
  продуктовые документы и если PR не вводит нового игрового поведения.
  Восстановление уже обещанного поведения исключением не является; если оно
  меняет картинку — мержи и дай владельцу однострочную команду запуска для
  ближайшего пакетного playtest. Всё остальное — включая любой `gameplay` и
  любой ADR — только по команде `MERGE #N`. Границы приняты ADR 0014.
- Любая команда запуска, выдаваемая владельцу, **проверяется до выдачи** и
  сопровождается двумя строками: что нового он увидит и что именно проверить.
  Команда указывает на рабочую копию, где изменение действительно есть, — корень
  репозитория только тогда, когда изменение уже в `main`. Правило и его причина —
  «Правила движения» в `docs/product/ROADMAP.md`.
- Публикация наружу требует явного разрешения владельца. Комментарии, Issues,
  PR и MR сначала показываются черновиком.
- Не начинай gameplay slice без решения `CONTINUE / ADJUST / PROMOTE / DEFER /
  STOP` по текущему.
- **В блоке обязателен gameplay-слайс.** Обеспечивающие задачи занимают
  оставшиеся слоты, а не заменяют содержание блока. Нет готового слайса — блок
  не начинается, начинается его подготовка (ADR 0018 §1).
- Одновременно проверяется **до двух** gameplay-слайсов, и только при трёх
  условиях (ADR 0018 §2): разные вопросы playtest; не делят балансную
  поверхность — балансные не параллелятся никогда; владелец знает до игры, что
  смотреть в каждом. Три и более не допускаются. Вопрос playtest формулируется
  **до выдачи задачи**, иначе условие непроверяемо.
- Глубина review — по тарифу ADR 0018 §3, не по усмотрению. `defect` и `support`
  вне контракта и детерминизма — один круг, потолок ~100k, второго круга нет.
  Обновления статуса проверяю сам, без субагента; ADR и продуктовые документы —
  всегда полный независимый review.
- Находка становится Issue только при наблюдаемом последствии; остальное — в
  `docs/engineering/DEBT_LEDGER.md` (ADR 0018 §4).
- **Одобрение прикрепляется к решению, а не к каждому PR** (ADR 0018 §7). Если
  владелец решение уже принял, PR, реализующий ровно его, мержу без второй
  просьбы при зелёных CI, `verify.ps1` и независимом review. Возвращаю ему:
  выход за пределы одобренного, новое решение, труднообратимое, новый риск,
  конфликт с ADR и любой новый ADR. Сомнение «покрыто ли это одобрением»
  разрешается в пользу вопроса. Gate этим не отменяется.
- В каждом блоке одна задача класса `art`, обслуживающая его gameplay-слайс:
  промпт формулирую я, генерирует Codex, подключает отдельный шаг `support`.
- Параллельно допустимы
  задачи других классов; потолок — **пять** записывающих агентов. Задача класса
  `art` в него не входит — её токены тратит другой инструмент. Review-агенты в
  потолок не входят, но их расход обязан называться: review стоит столько же,
  сколько записывающая задача, поэтому при полном потолке блок тратит примерно
  вдвое больше, чем следует из числа пять, и владельцу называется **суммарный
  расход**, а не количество агентов.
  Две записывающие задачи не владеют одним файлом: бриф каждой перечисляет её
  файлы и чужие файлы с указанием, кто их держит. Файловое правило **заменяет**
  правило областей, а не следует из него; единственное уцелевшее ограничение по
  областям — `art` держится целиком. Именованный регион вместо файла допускается
  только в `src/DungeonFortress.Game/Main.cs` и `scripts/verify.ps1`, при
  перечислении членов обеих сторон, названном владельце остатка, явном порядке
  merge и rebase на координаторе.
  Перед выдачей параллельных задач координатор **читает код**, чтобы список
  файлов был полным: первое применение правила пропустило `CameraView.cs`,
  нужный сразу двум задачам.
  Потолок и партиция приняты ADR 0017; потолок возвращается к двум без нового
  ADR при дефиците бюджета либо при появлении revert'а в `main`.
- Каждый PR получает независимый read-only review-агент до merge.
- Записывающая работа идёт в отдельной ветке `agent/<slug>` или worktree, а не
  в чужой рабочей копии.
- Существенное продуктовое, архитектурное или технологическое решение
  оформляется ADR, а не принимается молча в диалоге.
- Пользователю передаются только настоящие развилки: изменение продуктового
  обещания или scope, труднообратимое решение, новый риск, конфликт ADR либо
  нехватка полномочий. Обычные дефекты возвращай исполнителю сам.

## Что сделать в конце сессии

Убедись, что каждый значимый результат разговора попал в репозиторий: Issue,
ADR, раздел документа или PR. То, что осталось только в чате, считается
потерянным.

Перед merge любого PR проверь, что принятое в его обсуждении перенесено в
документ, ADR или Issue. Не успели перенести — запись уходит в coordination
inbox, а не остаётся в комментариях.
